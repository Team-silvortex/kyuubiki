## SQLite Shared Query Cache Follow-Up

This was an intermediate mitigation. The native-driver follow-up below supersedes
it and restores normal query caching after fixing the cleanup defect itself.

The earlier contention gap was reproduced after the test-lifecycle fix, rather than
being dismissed as a transient CI failure. With the original SQLite Repo policy,
the five-test project transaction file failed on round 18 of a fixed-seed repeated
run. The failure remained `database is locked` on `BEGIN IMMEDIATE TRANSACTION`.
An independent diagnostic with a fresh WAL database, two connections, eight
barrier-started callers and the unchanged 5,000-ms busy budget failed on round two.

Query telemetry showed a replay transaction holding the writer lock, completing
its receipt lookup, then waiting about 5.4 seconds before its next project lookup.
That next query's measured execution took only about two milliseconds. Another
connection's `BEGIN IMMEDIATE` expired during the gap. This was not a slow physical
solver or a slow SQL statement inside the transaction.

Inspection of the locked Ecto 3.14.1 / ecto_sqlite3 0.24.1 / Exqlite 0.38.0 stack
found that Ecto's per-Repo shared query cache retains `%Exqlite.Query{ref: ...}`
values. These native statement resources are tied to individual connections, while
Exqlite prepares a fresh statement on execution. SQLite Repo now defaults to Ecto's
supported `query_cache: false` option, keeping those handles out of the shared
cache. PostgreSQL policy, pool size, WAL mode, transaction isolation, busy budgets,
error propagation and explicit retry behavior are unchanged.

The cache path is implicated by repeated before/after evidence, but the exact native
wait cycle is not fully established. A controlled forced-GC experiment did not
reproduce the stall. A later call trace placed a 5.35-second gap after the writer's
`Exqlite.Sqlite3NIF.prepare/2` call while its competing writer waited in `execute/2`;
it did not establish a long Erlang GC event. Native resource cleanup/connection-lock
interaction remains an explanation to investigate, not a proven GC deadlock.
Re-enabling the original cache policy only inside a separate disposable diagnostic
process reproduced the failure again, on round 13 without call tracing and round 57
with call tracing. This does not modify the production source or the full-suite VM.

Two permanent regressions cover:

- Normal reads, aggregates, existence checks, bulk updates/deletes and transactional
  streaming preserve their results without populating the shared query cache.
- Two simultaneously checked-out connections query the same shape, perform repeated
  reads with explicit GC and leave no shared native query handles behind.

Temporarily restoring the original default policy made both new tests fail with
native handles visible in the cache. Restoring the fix made both pass. Existing
receipt rollback, explicit busy-error recovery, concurrent idempotency and reopen
tests remain enabled.

## SQLite Native Cleanup Root Cause

External sampling of the disposable diagnostic process captured the actual wait:

```text
normal scheduler:
  erts_schedule -> handle_aux_work -> run_resource_dtor
  -> statement_type_destructor -> erl_drv_mutex_lock -> mutex wait
dirty-I/O scheduler:
  exqlite_execute -> sqlite3_exec -> btreeBeginTrans
  -> exqlite_busy_handler -> sqlite3_sleep
```

The normal scheduler was blocked destroying a statement belonging to the connection
whose `BEGIN IMMEDIATE` was waiting for another transaction's write lock. The holder
could not resume on that scheduler to commit. The capture contained 1,622 samples of
the destructor wait over approximately two seconds. This is native resource cleanup
in scheduler auxiliary work, not necessarily an Erlang GC event. In-process sampling
was itself delayed, so only the external sampler captured the stall. That one
diagnostic used a 20-second busy wait to allow attachment; production and committed
regressions retain 5,000 ms.

More importantly, disabling query caching was not sufficient. A caller can return
its checkout, keep dead query terms until a later GC, and then destroy those terms
while another borrower is using the same connection. The new returned-checkout
regression failed on Exqlite 0.38.0 with query caching disabled: its first round
completed, then the second round timed out waiting for cleanup to yield. A separate
800-ms diagnostic observed about 853 ms for cleanup/yield and a competing writer's
`database is locked` error. The cache workaround therefore did not cover the whole
native resource lifecycle.

The matching defect is documented in
[upstream issue 360](https://github.com/elixir-sqlite/exqlite/issues/360).
[Exqlite 0.42.0](https://github.com/elixir-sqlite/exqlite/blob/v0.42.0/CHANGELOG.md)
defers cleanup when the connection is busy and drains pending statements when it
unlocks. The project now declares `exqlite ~> 0.42.0` explicitly and locks 0.42.0,
rather than relying on the adapter's older permissive transitive lower bound. No
other Hex package changed and no dependency source was locally patched.

The temporary `query_cache: false` Repo override has been removed. The controlled
cache-replacement diagnostic now succeeds with caching enabled, and the original
eight-caller/two-connection diagnostic completed 100 rounds without a lock failure.
The earlier tests that required an empty cache now verify functional results,
including distinct query parameters across simultaneously checked-out connections;
an empty cache is no longer the intended contract.

Two child-process regressions each execute five controlled interleavings with one
normal scheduler and two dirty-I/O schedulers:

- A writer replaces a query previously prepared by a now-competing connection,
  explicitly collects garbage and yields before committing.
- A reader returns its checkout, another caller borrows that connection for a
  competing write, and the reader collects its old query terms before the holder
  is allowed to commit.

Both require successful holder and waiter commits. The parent then reopens all ten
SQLite files and checks both writes, so neither a swallowed busy error nor an
uncommitted in-memory result satisfies the test. Barriers verify the competitor is
actually inside the native execute call before cleanup is triggered. The test does
not impose a benchmark latency threshold or retry a failed transaction.

### Child Environment Defect

The first Linux targeted run failed two of fourteen tests before reaching their
contention barriers: the expected single normal scheduler was actually four.
The parent test VM's `ERL_FLAGS=+S 4:4` was inherited by its children and overrode
their explicit `--erl` settings. This was a test-launch isolation defect, not a
new native SQLite lock failure. The same inheritance also affected the intended
resource limits of the disposable-database and forced-process-crash probes.

`TestSupport.BeamChild.port_env/1` now removes `ERL_FLAGS`, `ERL_AFLAGS`,
`ERL_ZFLAGS` and `ELIXIR_ERL_OPTIONS` only from the spawned VM environment.
All three probe families use this helper. Their explicit scheduler settings,
application environment, failure assertions and timeouts remain unchanged.
It does not mutate the parent environment or change production runtime settings.
This uses the environment-removal contract of
[`open_port/2`](https://www.erlang.org/doc/apps/erts/erlang.html#open_port/2),
rather than trying to outguess startup-argument precedence.

A new regression starts an intermediate disposable VM, populates all four startup
variables there, and compares an inheriting grandchild with an isolated one. It
requires scheduler counts `3:2:3` versus `1:1:2`, verifies all four flags are absent
only in the isolated child, preserves an explicit application marker, and checks
the intermediate parent's environment is unchanged. The main ExUnit VM's process
environment is never modified by this regression.
