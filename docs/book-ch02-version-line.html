What daji 3.x is optimizing for

Early Daji is hardening an agent-driven industrial research system, not maximizing feature count. At the current 3.5.0 checkpoint, progress means complete research journeys: bounded objectives, real execution, validated results, safe recovery, and reproducible evidence. Industrial reliability is the goal; each claim still requires its own proof.

Daji 3.5.0 checkpoint

  • Native Headless execution requires matching task completion, actual source bindings and contract-owned risk labels before downstream work.
  • Job waits validate identity and public state; result reads require a matching completed job and an explicit object result.
  • Lost or invalid write acknowledgements remain unknown with no automatic replay. Zero successful steps does not prove zero server-side effects.
  • Original-attempt inspection preserves identity and ownership. Expiry, eviction, endpoint loss and restart do not authorize fallback or reexecution.
  • New native submission checks require usable job IDs and consistent public status, even for complete 2xx replies. Malformed acknowledgements stop SDK/CLI chains without replay; submission does not certify a result.
  • Native library writes validate identities and requested objects/parents. Registered FEM saved-version solves keep server-side version association; a real seven-step chain checks computation and cleanup.
  • Saved model/version reads validate requested identity and parents before computation. Mixed inline/reference sources stop; native mesh fallback retains verified context without relabeling mutable models as versions.
  • Native job reads enforce explicit association hints and reject ambiguous options. Saved-version solve/wait retains its version constraint; result rereads do not resubmit computation.
  • Native submissions check transmitted project/version association before accepting a job. Orchestra rejects contradictory explicit pairs before job creation instead of silently selecting the checkpoint's project.
  • Single-job observation also checks exact identity, public state and caller association. Failed or cancelled jobs remain inspectable; a successful query is not successful computation.
  • Native HTTP reads and upload receipts have wire/header limits and nonrenewable network deadlines. Oversized writes remain unknown without replay; large result reads retain their separate budget and avoid one full non-chunked body copy.
  • Native batch bindings keep only later-referenced outputs, with independent fanout and ownership transfer on final use. A real SDK/CLI chain persists complete results in model versions without repeating computation; report summaries and failure gates are unchanged. This is not a process-wide RSS cap.
  • Native job/result and combined solve/wait normalization move original envelopes instead of deep-copying them again. Required public mirrors stay independent, full-result persistence is checked through SDK/CLI, and result admission/no-replay gates remain unchanged. No RSS or scale qualification is claimed.
  • Native inline JSON has one bounded encoded buffer, borrowed header/body vector writes and release before response reading. Oversize rejection remains pre-connect with exact byte diagnostics. Real SDK/CLI chains preserve complete multilingual notes; this is not a total memory/CPU cap or scale claim.
  • Native reports move eligible owned payload and unused result fields while retaining complete binding originals and independent previews. Sampling releases source capacity; thresholds and failure gates stay unchanged. SDK/CLI summaries match stored full data without extra computation, not an RSS/scale qualification.
  • Native Headless CLI JSON uses a 64 KiB encoding buffer and staged single-file replacement without old-report backups. Save failures retain available run receipts on writable stdout and never authorize replay. A real completed calculation recovers by reading its original job/result, not recomputing; power-loss and multi-file guarantees remain open.
  • Native CLI input/output reservations prevent source or evidence overwrite, duplicate outputs and file-as-parent collisions before execution, with another check at publication. Initial conflicts produce zero-step stdout receipts without file writes. Real service tests preserve source and project/job records with zero Agent calculations; hostile-directory and cross-platform qualification remain open.
  • Post-run material/evidence generation has a separate non-retryable diagnostic and retains completed run receipts. Metric labels cannot masquerade as job timeouts. A real bar result regenerates evidence through public SDK helpers without another calculation; successful computation alone is not qualified research output.
  • Research-round preflight validates effective inputs, metric step references and baseline/continuous lineage through a public Rust SDK function. The native CLI rejects static errors before service execution; real project/job state and two Agents remain untouched. Runtime result values and producer authenticity are not established by preflight.
  • Built-in material preflight checks all five fixed candidate sets, solver sources, owned waits and ordered result reads before service execution. Missing, repeated or misidentified sources leave real project/job state unchanged and perform zero Agent calculations. Grouped schedules remain supported; declared labels do not prove model fidelity or scientific qualification.
  • Fixed material reports now also require matching physical input profiles: constitutive properties, geometry, boundary conditions and composite coupling cannot silently reuse original factory constants after edits. Generic research, runtime context and annotations remain independent. Profile consistency is not scientific qualification.
  • Shared result-record diagnostic scans now cooperate with existing cancellation at entry, each 64 records and completion. Partial summaries cannot advance dependent actions. A native standalone TaskIR test preserves the cancelled attempt through one explicit successful rerun; JSON processing, plugins and durable restart remain outside this evidence.
  • Both independent Stokes diagnostic loops now use the same control helper. Cross-domain Engine tests cover thermal/electric/magnetic/thermo vector scans and stress-component fallback; cancelled execution scopes reject graph publication even with on_error skip. Explicit healthy runs recover, without qualifying non-transport Agent routing or durable continuation.
  • A separate native service follow-up extends the diagnostic/scoring whitelist to eleven Engine built-ins. Five study domains and a Stokes triangle chain execute sixteen jobs in 33 Agent executions; exact-target diagnostic cancellation and explicit recovery retain old failures in ten executions. Stokes RPC/program names now use the registry. This is not new TaskIR solver support, whole-job cancellation or installed/scale qualification.
  • Retained macOS and remote Linux source chains exercise actual commits, accepted calculations and withheld replies. Their original metadata and scope are not relabeled as fresh 3.5.0 qualification.
  • Earlier modal comparisons remain test-only. Solver retains numerical ownership, Engine/Agent retain execution authority, and installed or durable qualification gaps remain open.

Source and package metadata now target daji 3.5.0. This checkpoint does not rebuild or install binaries; the last local desktop and runtime baseline remains 3.4.0. Scoped numerical regressions do not establish external-solver correlation, general physical qualification, Windows, installed-Agent, GUI, or scale acceptance. The tiny-scale 128-element public solve still fails closed. Recompute affected historical modal results; tensor gaps remain open.

Agent-driven, with human control

Research agents use the Rust, Python, or Elixir Headless SDKs to orchestrate studies. Rust Agents independently execute admitted tasks through their local engines. Models cannot authorize their own plans, bypass resource limits, or turn an unvalidated result into evidence.

The acceptance loop is objective, capability discovery, validated workflow, authorized execution, observation and recovery, numerical review, then evidence export or a bounded next round. Workbench supports modeling, review, and human takeover of the same backend state. Pwdt automates the GUI but is not required for Headless operation.

Line posture

  • Keep major version posture conservative.
  • Prefer verified solver growth over speculative UI inflation.
  • Make release and automation behavior explicit instead of folklore-driven.
  • Carry forward open qualification work without promoting historical evidence to Daji.

What this means in practice

First harden one Installer-managed research journey, then deepen its numerical trust, failure recovery, replay, human review, and measured performance. Security and caller-owned approval apply throughout. Add new capabilities when they remove demonstrated blockers; do not lower tensor targets or platform release gates to claim completion.
