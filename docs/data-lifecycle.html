Kyuubiki Data Lifecycle

Keep research data independent of application upgrades

An application patch does not imply a data-format revision. When retaining data, migration must be explicit, inspectable and reversible by retaining the source. Disposable development data can instead be rebuilt. Installing an older binary is not a database downgrade.

Book Trust and safety Migration contracts

Development default: rebuild disposable data, do not accumulate backups

The current development workflow prioritizes project integrity and bounded disk use on both developer machines and test servers. Synthetic test data is not a permanent research archive. The preservation procedures below are opt-in for valuable, non-reproducible data or an explicit migration qualification; they are not a mandatory backup step for each patch, startup or cleanup.

  • Keep the reproducible project: source, dependency locks, contracts, fixture generators, regression tests and concise reports/logs/digests. Reuse isolated workspaces and compatible shared toolchain/build caches instead of retaining a complete source and build copy for every successful test round.
  • Remove completed-run bulk: generated mesh inputs, outputs, temporary databases and their sidecars, duplicate source trees and intermediate packages can be removed after checking ownership and active use. Do not create a cleanup backup. Keep only a small relevant failure fixture while investigating an unresolved defect, not every generation of the entire run.
  • Rebuild disposable legacy stores: stop all writers, select a fresh empty test database and initialize it with the current runtime. Remove the explicitly identified old test store when it is no longer in use; do not accumulate old stores under new names. For SQLite, use SQLITE_DATABASE_PATH for the fresh test path. Never delete WAL or journal sidecars while a database is active.
  • Keep safety without forced preservation: schema gates, transaction rollback, integrity checks and cleanup of owned staging remain. Backup commands run only when explicitly invoked. There is no new automatic reset, retention daemon, backup rotation or recursive user-folder cleaner.
  • Limit the scope: this policy covers known disposable development data, not unknown user projects, credentials, live services or unrelated containers. Decide retention explicitly for actual research. When pruning test artifacts, keep reports honest about historical evidence versus files still retained; a digest alone cannot reconstruct the original artifact.

Data classes and authority

These are lifecycle boundaries, not new editable configuration switches. Project-file migration and the scoped runtime-database lifecycle below are implemented; artifact, settings and credential migration remain separate work.

  • Projects: the user-selected .kyuubiki file owns project records, model versions, jobs, results, workspace state and attachments. The root project.json is the primary manifest; contradictory mirrors require explicit resolution. Owner: kyuubiki-project-bundle.
  • Research evidence and Kcore: retain immutable output artifacts, inputs, manifests, contracts and provenance together. Kcore verification is an existing exchange-format boundary, not permission to recompute or rewrite results. Owner: research SDKs and kyuubiki-kcore.
  • Runtime databases: Orchestra owns jobs, models, results and recovery state in its configured SQLite/Postgres backend. Central-store tables share that storage owner. Startup is now gated by a versioned migration ledger. Project commands must never be pointed at database files; use the database-specific maintenance API described below.
  • Recovery generations: existing persistence envelopes retain integrity-checked current/previous generations. Preserve recovery records and referenced artifacts together; a previous-generation fallback is not a schema downgrade or proof of cross-version recovery.
  • User preferences and drafts: Hub/Workbench/Installer own their settings and browser state. Portable export and schema migration of those stores remain separate work. Do not classify unsaved drafts as disposable caches.
  • Packages and caches: Installer owns sealed runtime/package generations; the bound Orchestra owns the authoritative operator library. Agent download caches may be rebuilt only under their existing ownership and eviction rules. Installer rollback must not roll back scientific data silently.
  • Credentials: vaults, tokens, certificates and native secure-store handles are outside ordinary project migration. This is not a secret scanner: opaque attachments are preserved, even if a user put sensitive data in them. Credential transfer needs explicit re-enrollment or a separate encrypted export.
  • Logs and audit trails: diagnostic logs follow retention policy; research provenance and mutation audit trails are not disposable debug output. Source paths, server addresses and credentials are not embedded in migration receipts.

Result and workflow recovery round trips

JSON persistence and workflow recovery digests use the same Storage.DurableJson object-key rules as the actual JSON encoder. In particular, the Elixir nil key becomes "nil", not an empty string. Nested atom/string or integer/string key aliases that would produce duplicate JSON keys are refused before publication. Recovery preparation and verification return a controlled error for these ambiguous native values.

The existing v1 envelope schemas remain unchanged. String-key records retain their previous digest behavior and are read without rewriting. Scientific number serialization is not rounded to repair a checksum. TaskIR's separate canonical encoding contract is unchanged. Previously inconsistent nil-key digests are still rejected: a new checksum over suspect bytes would not prove those bytes are the original research result. Regenerate disposable fixtures or explicitly investigate valuable data instead of silently accepting it.

Generic ranking and Pareto summaries remain in diagnostics bundles even without a diagnostic domain. bundle_domain_counts counts declared domains only, consistent with bundle_domains; bundle_source_count still includes every source. No artificial null domain or automatic scientific-data rewrite is introduced.

The material-envelope API regression now checks completion, result-file publication, independent disk readback and a subsequent generation write. This is scoped persistence/recovery evidence, not power-loss, multi-writer or installed cross-platform qualification. See the verification report.

Model checkpoints and project export

A model's current payload is a working copy, distinct from its stored checkpoints. Deleting a checkpoint repairs latest_version_id and latest_version_number to the highest remaining version without reverting the working payload. Removing the last checkpoint leaves a usable model with a null latest ID and number zero. A later save creates a fresh version ID.

Use version_id as the identity in jobs and external references, not version_number. Numbers order the current checkpoint list; after deleting its newest entries, a number can be used again with a different ID. Existing duplicate numbers or dangling historical records are not automatically rewritten by this change.

SQL model creation and its initial checkpoint now publish in one transaction. Checkpoint creation and deletion update the latest pointer in the same transaction; SQLite uses an immediate transaction and PostgreSQL locks the parent model row before allocating a number. Failed publication rolls back both sides and can be retried without a partial model or orphan checkpoint. The initial checkpoint label does not replace the requested model name.

Project export selects an active version only from the active model. A model without checkpoints exports a null active version rather than a checkpoint belonging to a different model. This does not make a live multi-query export an atomic database snapshot or add a new import endpoint. See the project/version chain regression report for API reconstruction, concurrency and rollback scope.

For project-bound execution, submit project_id and model_version_id alongside the solver payload or catalog input_artifacts. Direct solvers, raw graphs and catalog workflows preserve this context. A selected version determines the owning project; a missing or deleted version is rejected with HTTP 422 before creating a job. Version IDs are provenance metadata, not automatic input loading: explicitly fetch and submit the selected checkpoint payload, rather than the edited working copy. No payload-to-checkpoint digest equivalence is implied.

Exported workflow records may contain failure diagnostics and recovery history, not just successful outputs. Check the job status and workflow recovery.state; has_result alone does not mean the solve succeeded. Deleting a job also removes its result. Reading a missing job or its /status endpoint now returns HTTP 404 with {"error":"job_not_found"}, consistent with other job operations, rather than the previous generic HTTP 422 response. See the native project execution chain report for analytical checks, failed-solve recovery and model reconstruction on macOS and Linux.

Bounded desktop checkpoint recovery metadata

The Workbench native host owns desktop-checkpoint-recovery.json under the platform's Kyuubiki desktop-preferences root. Its version-1 record permits only 64 entries and 64 KiB total serialized data. Entries contain a content/scope digest, operation, parent ID, request ID and creation time, never credentials, backend URLs, model names or geometry. This is not a snapshot, backup or unsaved-draft archive.

Each read-modify-write takes the fixed desktop-checkpoint-recovery.lock. A single bounded desktop-checkpoint-recovery.pending file is synchronized before atomic replacement, then the directory is synchronized. Unix files are created mode 0600. Unsafe file types/symlinks, corruption and full capacity fail closed rather than resetting the record or evicting uncertain saves. Stale staging is reused only under the lock after regular-file validation; there is no growing backup series.

The embedded page can invoke only list, reserve and conditional remove through a source-and-origin-pinned bridge, with a bounded queue and field validation on both sides. It cannot provide a filesystem path or arbitrary native command. The recovery UI uses read-only GET /api/v1/checkpoints/:operation/:parent_id/:request_id with the existing read authorization and Cache-Control: no-store. Acknowledgement removes only an exact confirmed or deleted identity; unknown outcomes remain pending.

Normal browser mode uses the bounded IndexedDB database kyuubiki-checkpoint-recovery; desktop host failure never falls back to it. Entries from a different backend/authentication scope remain isolated and still count toward capacity. Do not delete the journal as routine cache cleanup: reconcile against the original authority first. Current native evidence verifies clean macOS process exit, not hard power loss, concurrent-window end-to-end reconciliation or all-platform storage. See the PWDT recovery tutorial.

Implemented: offline project migration

The native Rust library exposes plan_project_migration, migrate_project_bundle and verify_project_migration. The native command runner is a thin adapter; no Node process, browser, Orchestra or Agent is required.

  1. Stop all writers and retain the source file. Input is a regular .json or .kyuubiki file. Mutable directories, symlink sources, live stores and other formats are refused.
  2. Run the read-only plan. Review its actual source schema, status, changed root fields, source SHA-256, limits and issues. Archive entry integrity is scanned. Plan scope is root structure plus source inventory, not physical validation or complete JSON-Schema conformance; mirror reconciliation also runs on apply.
  3. Approve the exact source digest and choose a new output. Migration snapshots source bytes into a private sibling staging directory, rechecks the digest, upgrades metadata, materializes the standard layout, and reconciles mirrors.
  4. Opaque attachments and prior receipts are retained byte-for-byte. Existing model/result mirrors must agree with the root. Workspace schema metadata can advance from v1 to v2 without dropping extra preference fields. Missing derived catalogs may be built; malformed arrays and conflicting scientific records are never replaced with empty/default values.
  5. All candidate entry digests and the full manifest are read back. The source digest is checked again. A synced complete candidate is published with an atomic no-overwrite hard link in the destination filesystem. Unsupported hard-link filesystems fail closed; there is no unsafe rename/copy fallback.
  6. Retain the external JSON receipt alongside the output, then verify after a transfer or move. Its output digest binds the entire archive. An embedded record retains source digest, source/target schemas, changed and preserved entries, migration ID and timestamp. It omits publication fields to avoid a self-digest.
  7. To roll back, reopen the retained source with a compatible reader. Do not merge post-migration edits back automatically. Deleting either copy is a separate operator decision, never an upgrade side effect.
cargo kyuubiki project migration-plan studies/original.kyuubiki --json
cargo kyuubiki project migrate studies/original.kyuubiki \
  --out studies/upgraded.kyuubiki --expect-source-sha256 <reviewed-source-sha256> \
  > studies/migration-receipt.json
cargo kyuubiki project migration-verify studies/upgraded.kyuubiki \
  --receipt studies/migration-receipt.json

The commands print JSON. A blocked plan returns exit 1; migration/verification errors return a nonzero exit. Existing output files, dangling symlinks and concurrently created target names are not overwritten. The caller must also avoid overwriting a receipt via shell redirection.

Compatibility policy

  • kyuubiki.project/v1: explicit copy migration to v2. Existing readers may still adapt v1 in memory; reading alone does not rewrite the source.
  • kyuubiki.project/v2: current format. Missing optional fields are reported as normalization_required. A deliberate copy of current data adds a receipt without incrementing the data schema.
  • Unknown project versions or layouts: blocked, no best-effort downgrade. The only supported layout is kyuubiki.project-layout/v1.
  • Unknown extension data: retained, not executed or interpreted. Migration does not certify that an older reader can use that extension or embedded model.
  • Scientific values, identities, result payloads and record ordering are not intentionally changed. JSON formatting and equivalent numeric spelling may change; this is not a numerical solver or material calibration step.
  • Digest verification assumes a separately trusted receipt. An attacker who can replace both archive and receipt is outside hash-only integrity protection.

Visible limits and failure behavior

Default ProjectMigrationLimits: 4 GiB source/output file, 64 MiB per parsed/generated JSON document, 8 GiB expanded archive content, 100,000 entries. Rust callers can pass explicit limits; the plan records them. These are safety budgets, not million-node workload qualification.

Migration needs space for a source snapshot, generated canonical archive and final candidate. Source and destination may be on different volumes; staging and final publication must share the destination filesystem. On Unix, staging uses mode 0700 and the output uses mode 0600. Common traversal, reserved device, case-collision and file/directory aliases are rejected. No archive is extracted to arbitrary paths by this flow.

Normal pre-publication errors remove the owned staging tree and leave no final candidate. A kill/power loss may leave a private .kyuubiki-migrate-<uuid> directory beside the target. It is never considered published data. Stop the migration process, retain/verify the source and any published output, then remove only that owned staging directory. There is no age-based recursive cleanup of user folders.

If ordinary staging cleanup fails, the error names the pending sibling directory; after successful publication, cleanup_pending in the returned receipt exposes that residue instead. Publication is not undone merely because cleanup or a directory sync failed.

The returned directory_synced publication field is true only when parent-directory sync succeeds. False means the complete file is published but directory-entry power-loss durability is not confirmed. That field is absent from the earlier embedded record. Windows ACLs, Unicode filesystem normalization, network-filesystem crash semantics and real power loss require platform qualification; a successful unit test is not such a qualification.

Physical ZIP/ZIP64 directory bounds and entry counts are checked before the ZIP library builds its name map, so duplicate names cannot disappear through map deduplication. Encrypted, multi-volume, ambiguous-trailer and legacy non-UTF-8 filename archives require separate explicit conversion, not best-effort rewriting during this migration.

Implemented: runtime database version gate

Storage.SchemaSetup now calls DatabaseMigrations.boot! before the application starts recovery workers or HTTP listeners. SQLite and PostgreSQL use the same migration definition and shape policy, with backend-specific SQL. No new Rust or Node database owner is introduced alongside the existing Elixir/Ecto service.

  • A genuinely empty database is initialized in one transaction. The kyuubiki_data_migrations ledger records data version, immutable migration ID/checksum, minimum reader version and application time. Data version 2 is independent of the product's release number. The original runtime-baseline-0001 recipe and checksum remain unchanged.
  • A known current ledger is checked, never rewritten merely on restart. Missing managed tables, incompatible column types/nullability/primary keys/foreign-key contracts, unknown managed tables or columns, malformed ledgers and future history fail before application schema changes or business writes. Opening the Ecto connection may still update SQLite journal metadata before this gate; startup is not a byte-read-only inspection. This is not an audit of every index, trigger, default expression, privilege or all research payloads.
  • An existing unversioned Kyuubiki database now deliberately blocks startup. For disposable development data, initialize a fresh empty test database as described above. To retain valuable data, take a consistent snapshot, upgrade a separate candidate and verify it first. Reinstalling an old binary is not an approved database downgrade. Older binaries without this gate cannot be forced to obey it; isolate them operationally.
  • The baseline preserves existing records and can add the four known missing legacy job columns: model_version_id, queue_timeout_ms, execution_timeout_ms and execution_started_at. Only missing known legacy tables are materialized; versioned databases are not silently repaired. Unknown extensions in managed tables require conversion.
  • Revision 2, runtime-checkpoint-requests-0002, adds kyuubiki_checkpoint_requests for idempotent model/checkpoint creation. Receipts contain request digests, resource IDs and small response metadata, not another geometry payload. They survive model/version deletion and are removed with the project. Receipt and research-data writes share one transaction.
  • A valid revision-1 ledger reports upgrade_required and startup refuses writes until an explicit candidate upgrade. It is not silently upgraded on restart. Use the existing digest-approved copy-upgrade and verification procedure below, stop every writer, then explicitly switch the service database. A clean empty development database initializes both revisions atomically. Trusted revision-1 snapshot receipts remain independently verifiable; their old reader target is checked against the known immutable baseline, not rewritten to appear current.
  • SQLite uses an immediate transaction; PostgreSQL uses a transaction-scoped advisory lock. DDL and ledger writes commit together or roll back together. The lock coordinates cooperating migrators, not arbitrary old application writers. Stop every writer before service activation or maintenance on a clone.
  • Future revisions must append an explicit migration and compatibility rule, with fixtures and qualification. Never edit the pinned baseline recipe or manually stamp an unknown database as current.

SQLite backup, copy upgrade and restore

Use this workflow when data preservation is required, or when testing migration itself. For ordinary disposable development fixtures, prefer rebuilding and cleaning the previous test store instead of retaining these copies.

KyuubikiWeb.Storage.SqliteLifecycle exposes backup!, plan!, upgrade!, restore! and verify!. The Mix adapter starts dependencies only, not Orchestra or its HTTP listener. The same library can be called by an installed BEAM maintenance process with Exqlite and crypto started; Mix is a development adapter, not a new runtime shell/Node dependency.

# Run from apps/web. All output paths below must be new.
mix kyuubiki.data backup path/to/active.sqlite3 --out path/to/snapshot.sqlite3
mix kyuubiki.data plan path/to/snapshot.sqlite3
mix kyuubiki.data upgrade path/to/snapshot.sqlite3 \
  --out path/to/candidate.sqlite3 --expect-sha256 <reviewed-snapshot-sha256>
mix kyuubiki.data verify path/to/candidate.sqlite3 --receipt path/to/upgrade-receipt.json
mix kyuubiki.data restore path/to/snapshot.sqlite3 \
  --out path/to/restored.sqlite3 --expect-sha256 <reviewed-snapshot-sha256>
  1. Keep each JSON receipt printed by backup/upgrade/restore. Use a unique receipt filename if redirecting output. Compilation notices may precede JSON on the first Mix invocation; compile first for machine consumption. Prefer the direct library API for integration.
  2. backup! reads through SQLite and uses parameter-bound VACUUM INTO to construct a consistent standalone snapshot, including committed WAL pages. It does not copy only the live main file. The source is opened read-only, though SQLite may need shared-memory sidecar access. The snapshot is logically equivalent, not necessarily byte-identical; implicit SQLite ROWIDs are not a portable application identity.
  3. A backup is one point in time. Stop writers and take a final backup before switching services, otherwise writes made after that snapshot are not in the new database. This increment does not implement online delta synchronization.
  4. Plan/upgrade/restore require a standalone file without active WAL/journal content. Approval binds the whole snapshot SHA-256. Upgrades copy into a private candidate, verify that digest, migrate transactionally, check SQLite integrity and foreign-key consistency, then read the resulting plan back.
  5. A synced complete candidate is published by an atomic no-overwrite hard link. Existing outputs and sidecars, source symlinks and dangling destinations are refused. Unsupported hard-link filesystems fail closed. Unix staging/output permissions are 0700/0600; Windows ACLs remain unqualified.
  6. Verify uses a separately trusted receipt, output digest, byte count and actual database plan. Moving a snapshot does not invalidate its receipt. Hashes are integrity evidence, not signatures; they do not resist replacing both artifacts.
  7. After stopping writers, explicitly select the verified database through SQLITE_DATABASE_PATH, then start one compatible runtime and perform a read/write health check. None of these commands changes configuration, starts services or selects the candidate automatically.
  8. Restore produces an exact separate copy of an approved standalone snapshot. A restored legacy database still needs a compatible old reader or explicit upgrade. Recovery is not automatic merging of changes made after the snapshot. Keep both the old database and receipts until the retention decision is explicit.

The current safety limit is 16 GiB per main file or sidecar and per resulting snapshot. This is not a disk reservation or hard runtime quota: concurrent growth and SQLite temporary work require additional free space. Copy/hash operations stream in 1 MiB chunks; backup and integrity-check latency require workload qualification. Ordinary failures clean owned staging. A hard kill can leave .kyuubiki-data-* beside the destination: stop the writer, verify retained source/published output, then remove only that owned stage. Cleanup errors report residue explicitly. A published output still returns its receipt with cleanup_pending if only staging cleanup failed; never interpret an error as permission to overwrite an output that might already have been published.

directory_synced=false means publication occurred but parent-directory power-loss durability was not confirmed. Snapshot consistency does not prove hardware, filesystem, ENOSPC or hard power-loss recovery. Database snapshots exclude external result files, Kcore artifacts, workflow recovery envelopes, credentials and package caches; retain their corresponding generation separately. This is not yet a whole-system backup.

PostgreSQL shares the ledger, schema gate and transactional candidate-adoption API. Its integrated backup/restore command is still pending. An operator must first restore a proper PostgreSQL backup into an isolated database and own that candidate before calling upgrade_candidate!; do not pass the active repository. Remote tests use disposable databases, not production tables.

Underlying semantics: SQLite VACUUM INTO and PostgreSQL advisory locking. Output contracts: database lifecycle schema.
