The hard architecture boundaries

Kyuubiki depends on preserving splits between frontend, Hub, Workbench, Installer, orchestrator, and agents. The agent is not the UI, the Workbench is not the runtime, and the Hub is not the orchestrator.

Back to book Previous chapter Next chapter

Boundary rules

  • Hub manages entry, operator flow, runtime switching, and packaging posture.
  • Workbench owns the concrete analysis workflow and authoring surface.
  • Installer owns deployment structure and installation policy.
  • Agents stay runtime-side, headless, and Rust-first.
  • One orchestrator controls an agent at a time unless the system is intentionally in decentralized mesh mode.

Why these boundaries exist

Once roles blur, automation, deployment, and distributed execution all get harder to reason about. The system becomes easier to extend when ownership and authority stay visible.

Coverage tensor: evidence without overclaiming

Recalibrated September 13, 2026 for the daji 3.2.x hardening profile, with source checkpoint daji 3.2.0. The three axes remain module, function paradigm, and scoped evidence depth: 13 modules, 11 paradigms, and 77 required coordinates. Recalculation reviews retained claims; it does not rerun the product tests those claims describe.

  • Registered benchmark and security commands are plans, not proof that a test ran.
  • A coordinate uses its weakest required dimension, not its highest single claim. Stronger evidence remains visible as best_available_grade.
  • Explicit platform, backend, SDK-language and recovery scenarios require named proof bindings. An empty binding remains open even when other evidence is operational.
  • Target attainment requires covered capability, sufficient dimension grades, and all configured scenario obligations. A zero grade-step gap alone is not success.
  • Structural success, evidence maturity, and release permission are separate. Release thresholds use exact counts rather than rounded display percentages.
