The hard architecture boundaries

Kyuubiki depends on preserving splits between frontend, Hub, Workbench, Installer, orchestrator, and agents. The agent is not the UI, the Workbench is not the runtime, and the Hub is not the orchestrator.

Back to book Previous chapter Next chapter

Boundary rules

  • Hub manages entry, operator flow, runtime switching, and packaging posture.
  • Workbench owns the concrete analysis workflow and authoring surface.
  • Installer owns deployment structure and installation policy.
  • Agents stay runtime-side, headless, and Rust-first.
  • One orchestrator controls an agent at a time unless the system is intentionally in decentralized mesh mode.

Why these boundaries exist

Once roles blur, automation, deployment, and distributed execution all get harder to reason about. The system becomes easier to extend when ownership and authority stay visible.

One owner per responsibility

The October 23, 2026 organization review separates three views: 13 logical topology modules, 15 Rust workspace crates, and independently deployed processes. They are not the same count. Engine and Solver are libraries used by the Agent; keeping their responsibilities separate does not require another service. Hub, Workbench and Installer remain independent Apps sharing native lifecycle and UI helper code.

  • GUI and Headless SDKs are clients. PWDT automates the fixed UI; the Rust-only Worker / Operator SDK extends executable operators.
  • Orchestra owns coordination and persistence. Direct Agent and explicit offline Mesh paths are separate supported architecture paths, not requests to embed Orchestra in the GUI.
  • Agent owns process, ingress and receipt boundaries; Engine owns execution dispatch; Solver owns numerical algorithms and acceptance.
  • TaskIR execute is implemented behind capability and package gates. A successful preflight is not a completed solve, and source-IP containment is not cryptographic peer authentication.
  • The current map owns navigation. Current-line notes and dated reports own progress; the tensor owns scoped evidence requirements.

Numerical acceptance has one runtime owner

Solver owns numerical admission; Engine owns dispatch and workflows; Agent owns execution identity and transport. A GUI or Headless client must not implement a second residual policy or silently relax a failed kernel gate. TaskIR capability admission remains a separate boundary.

  • Coordinate and prescribed constraints use shared complete-system checks after restoration; support reactions need not vanish.
  • Directional thermal-frame supports keep their projected identities, admissible-direction equilibrium and physical reaction recovery.
  • Newmark checks the full velocity increment against the original effective system before state/history updates.
  • Newton checks the full unscaled correction against the current tangent and residual before line search. Complete nonlinear states also check dimensions, finite values and fixed support identity.
  • Harmonic spring checks the complete complex state and original element/mass/load equations at every frequency. Binary product scaling must not erase finite forces or change fixed supports. Frequency products must also retain finite inertia and acceleration even when the intermediate angular-frequency square is out of range. Complex substitution replays complete exceptional rows before pivot division; element-force products combine terms before restoration.
  • These are named consumer scopes, not all-operator qualification. Cooperative cancellation/replay is not durable restart evidence.

Build output is not runtime state

Preview rebuildable caches with make disk-usage; use make clean-dev-cache explicitly while builds and tests are idle. The native cleaner holds Cargo locks and preserves dependency libraries, top-level tools, release packages and runtime data. Test executables may need relinking afterwards; hard links mean the logical preview is not an exact prediction of freed disk space.

Do not delete tmp/ wholesale: it mixes disposable reports with databases, journals, execution receipts and process ownership records. Git ignore status is not a retention policy. Installed Apps, credentials and server storage belong to separate Installer-managed lifecycles, not repository cache cleanup.
