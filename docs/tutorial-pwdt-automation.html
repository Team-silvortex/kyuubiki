Automate the fixed Workbench UI

PWDT runs Python through Pyodide inside the WebView and invokes the same product-owned actions as the GUI. It is the frontend automation surface, not a solver SDK and not a replacement for headless service control.

Recipes are versioned product paths assembled from registered actions. Use explicit actions when exploring or debugging; use a recipe when its completion contract matches the workflow you need.

Waiting and failure rules

  • Await every state-changing action. The Workbench action bridge waits for the UI state commit before resolving, so the next action uses the updated project, model, selection, and parameters.
  • Wait on observable state with wait_for_job_done, wait_for_message, or wait_until; do not add arbitrary sleeps around network work.
  • wait_for_job_done reports any terminal state, including failure or cancellation. run_current_study requires success and raises on failure instead. All five built-in recipes enforce this at every stage, before projection, another save, or opening results. They do not automatically retry a solver submission; completed input saves remain available for inspection.
  • ky.state()["hasResult"] is a boolean for the recognized active result, including two-dimensional heat and electrostatic results. It is not a count of archived results and is cleared when switching to another study. Clearing the current view does not cancel backend jobs or delete archived records.
  • Use sleep only for bounded UI settling where no stronger state exists.
  • High-risk actions still require product confirmation. PWDT does not create hidden authority.
  • If an action is absent, stop and inspect the parity report instead of clicking a similarly named element.
  • If a run fails, preserve the action log and current snapshot before replaying any step.

Runtime loading recovery

  • If the Pyodide script download or initialization fails, inspect the runtime error and use Load runtime again. Reloading the page is not required, and the editor source is preserved.
  • The script download has a 30-second timeout. Failed script tags and failed initialization promises are discarded so that a new explicit attempt can proceed; simultaneous loaders share one attempt.
  • A Python script error does not discard a successfully initialized runtime. Fix the script and run it again; earlier GUI actions or backend writes are not rolled back automatically.

Recovery tests use intercepted script downloads and a runtime adapter. They verify the GUI loading and retry path, not an actual Pyodide WebAssembly download or Python numerical execution.

Concurrent project operations

  • Model and version loads use the latest workspace operation. A late response cannot replace a newer load or a different selected project; stale failures do not overwrite that workspace's message.
  • A save already sent to the backend still belongs to its original project and model. If the workspace changes before the response is applied, the save action returns its persisted ID with ok: true and contextChanged: true, without selecting the old model again. Inspect the original project before retrying; do not assume that the write failed.
  • Project creation, update and deletion, saved-model deletion, and version rename and deletion follow the same rule in GUI and PWDT. Completed stale writes return the original affected ID with contextChanged: true; they do not select another project, reset its drafts, or replace its feedback. Failed writes still reject rather than report success.
  • Deletion reconciles associations by resource identity: deleting the active project detaches its project, model, and version; deleting the active model detaches that model and version; deleting a version detaches only that version. This also applies if you switched to another version within the deleted project or model. The working model remains available, but saving a detached copy cannot silently overwrite a different saved model. An unrelated selected resource remains untouched.
  • Completion checks cover the final version-list refresh as well as the initial write or load. Switching away and back still invalidates the operation; committing its own newly saved or loaded selection does not.
  • Built-in macros, run_steps, and all five built-in research recipes stop remaining steps when an action reports contextChanged. This applies to both browser PWDT and Python PWDT, including project creation and each intermediate save in composite recipes. The completed write is retained; inspect it before retrying rather than generating duplicates. Superseded loads fail with WORKBENCH_CONTEXT_CHANGED.
  • Direct invoke and save_model callers still receive the affected ID and completion flag. Check contextChanged before continuing a dependent action. ensure_project stops with an error if a newly created project could not become the active workspace, rather than silently continuing in another project.
  • A bundle import that has begun creating records finishes in its new project, but does not replace a workspace selected while the import was pending. The imported project remains available in the refreshed library.
  • Catalog refresh preserves newer selection. It does not load model geometry, so it never attaches an unbound working model to the first saved model; open that saved model explicitly instead. If refreshing fails, the last usable catalog remains visible with runtime recovery feedback; this does not claim the cached catalog is current.

These boundaries are exercised by isolated browser tests with delayed and failed API responses. The shipped Python prelude is also executed against an in-memory JavaScript bridge adapter, not just inspected as text. That frontend test requires Python 3 (CI uses 3.12); it does not add a native Python dependency to the application. These checks do not qualify Pyodide downloads or WebAssembly startup, packaged WebViews, real database transactions, or numerical solver accuracy.

Stable selector escape hatch

Prefer actions and recipes. When a read-only UI assertion truly needs a selector, resolve it through the product UI contract instead of writing a CSS selector tied to layout or translated copy. 

selector = ky.ui_selector("runtimeTab", "control")
panel = ky.query_selector("runtimePanel")
tabs = ky.query_selector_all("runtimeTab", "overview")

Completion contract

  • The script checks capabilities before mutation.
  • The same project, model, terminal run, and result exist as in the manual tutorial.
  • No localized copy, layout class, or raw DOM path is used as an action contract.
  • The action timeline identifies the failing action if the loop does not complete.
  • Project bundle exports include only jobs explicitly assigned to the selected project. Other projects and unassigned runtime jobs are not included.
  • Switching to another existing project detaches the current saved-model and version IDs, while keeping the working geometry available to save into the new project. Unknown project IDs fail without changing the active context.
  • Bundle import validates the file sections and active workspace payload before creating records. Model and version IDs are remapped to the imported project; the workspace name and selected older version are retained, so the next save continues that model instead of duplicating it.
  • If an expected result is unavailable or mismatched, export returns partial: true and the GUI shows the existing partial-export warning. Keep the available data and retry after the service recovers.
