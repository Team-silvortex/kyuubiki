Automate the fixed Workbench UI

PWDT runs Python through Pyodide inside the WebView and invokes the same product-owned actions as the GUI. It is the frontend automation surface, not a solver SDK and not a replacement for headless service control.

Resize the workspace without changing the UI contract

On desktop, drag the separators beside the tool sidebar and inspector, or above the expanded report, to resize these built-in panels. The viewport keeps a minimum share of the window and fits the model inside the remaining space. Compact stacked layouts hide the separators without erasing your desktop preferences.

Double-click a separator to reset that panel. The layout icon in the report header resets all three sizes. Focus a separator and use arrow keys for 10-pixel steps, Shift+Arrow for 40-pixel steps, or Home/End for its safe limits. Escape, pointer cancellation, window resizing, and loss of focus cancel an unfinished drag.

Sizes are saved after an explicit adjustment. In a browser, the preference is kyuubiki.workbench.panelLayout.v1. In the desktop shell, the authoritative copy is desktop-workbench-layout.json in the native application preferences directory; WebView storage is only a cache. The record contains a version and up to three numeric dimensions, never models, results, credentials, or an arbitrary file path. Window constraints do not overwrite preferred sizes.

The native preferences directory is $HOME/Library/Application Support/kyuubiki on macOS, %APPDATA%/kyuubiki on Windows, and $XDG_CONFIG_HOME/kyuubiki (or $HOME/.config/kyuubiki) on Linux. It is outside versioned runtime payloads. Native writes atomically replace the complete bounded record. Restore layout commits an empty sizes object so stale WebView caches cannot resurrect an old layout.

The desktop bridge checks both the embedded frame identity and its pinned loopback origin. Only the two panel-layout commands are exposed through it; remote native IPC permissions and WebView isolation are unchanged. Delayed reads cannot overwrite newer adjustments, and busy writes coalesce to the newest committed layout. If storage fails, live resizing remains available without claiming a durable save.

Current qualification: browser reload and installed macOS application quit/relaunch persistence are verified, including restoration of all three dimensions and resetting them across another relaunch. Windows and Linux use the same contract but have not been requalified on native devices for this change. The shell's data-workbench-layout-storage attribute distinguishes native-loading, native-saving, native, browser saved, and fallback memory.

PWDT's UI contract exposes sidebarResize, inspectorResize, reportResize, and layoutReset. Existing panel and action selectors remain unchanged: resizing does not make the product-owned UI extensible.

Batch modeling without individual clicks

Open Workspace / Tools / Studio / Batch modeling. The same commands are registered as state/inspectModelBatch and state/applyModelBatch for PWDT. Current support is limited to truss_2d, truss_3d, and frame_2d; other studies return model_batch:unsupported_study rather than editing an inactive mechanical model.

Choose the current selection, all nodes, zero-based indices such as 0-9, 15, 20-30, or an inclusive coordinate interval. Inversion applies to the entire working model, including hidden nodes, not just the rendered viewport slice. The preview counts matching nodes, members with both endpoints inside the group, and members with at least one endpoint inside.

  • Translate: add an offset vector in metres. Align: set one coordinate. Loads remain in the original global axes. Creating a zero or near-zero-length affected member is rejected atomically.
  • Rotate / scale / mirror: edit the selected geometry in place or set copy: true to create one transformed copy with internal members only. Each transform requires a pivot: {"kind":"origin"}, {"kind":"selection"} (the selected nodes' axis-aligned bounds center, not their centroid), or {"kind":"point","point":{"x":0,"y":0,"z":0}}. The pivot is resolved once from the source selection. Copies may overlap the source; there is no implicit welding or collision check.
  • Rotation: axis is a global X/Y/Z axis through the pivot, with right-hand angleDegrees. Quarter turns are exact; arbitrary angles use floating-point trigonometry. Planar trusses and frames allow rotation about Z only and do not acquire a Z coordinate. For a multi-step rotation sequence, use an explicit point if the pivot must stay fixed: recomputing selection bounds after a rotation can move their center. Undo restores the exact prior geometry.
  • Scaling: factors are positive, dimensionless X/Y/Z multipliers about the pivot; an omitted Z factor is 1. Set equal factors for uniform scaling. Zero and negative factors are rejected; use mirror for reflection. Node positions change, but member areas, inertia, section moduli, materials, loads, supports and frame moments are not automatically scaled or rotated. This is a geometry editor, not a physical similarity transformation.
  • Mirror: axis: "x" reflects across the YZ-parallel plane at the pivot's X coordinate; Y reflects across XZ and Z across XY. The GUI labels these planes explicitly. Planar studies allow X/Y reflection only. Existing endpoint order and member properties are preserved.
  • Snap: {"kind":"snap","axes":["x","y","z"],"spacing":0.1} snaps selected coordinates to a world-origin grid in metres. Only listed axes change; half steps round away from zero. A nonpositive spacing, unrepresentable grid index, or collapsed incident member rejects the whole batch. Snapping neither merges coincident nodes nor synchronizes the decorative viewport grid.
  • Linear array: copies counts additional copies. Copy k uses offset * k. Only internal members are duplicated; endpoints are remapped, existing IDs preserved, and new IDs avoid collisions. There is no automatic bridging, node welding, intersection test, or support inference.
  • Copy boundaries: off by default. Copies clear nodal loads and supports, including frame rotation restraints and moments, and an existing frame distributed Y load. copyBoundaryConditions: true explicitly retains them. Material and section properties are retained either way. Review constraints and connectivity before solving.
  • Loads: force values in newtons replace the selected nodes' force components. distribution: "total" divides the resultant equally across the group; "per_node" assigns the entire vector to each node. Zero clears those forces; frame moments remain unchanged.
  • Supports: fix or release only listed axes. Z is supported for 3D trusses and rz for 2D frames. Unlisted constraints remain unchanged.
  • Members: choose scope: "internal" or "touching". Set a positive cross-sectional area in square metres, assign an existing material, or both. Material assignment also updates inline Young's modulus. Omitted fields and unrelated members remain unchanged.
  • Delete: removes matching nodes and all incident members, then remaps surviving endpoints without renaming objects. GUI confirmation is invalidated by model or selection changes. PWDT requires operation.confirmDelete: true. An empty working model is permitted for editing, not for solving.

The viewport's existing quick Duplicate and Mirror buttons now share batch identity and topology guards. Quick Duplicate retains its fixed (0.4, 0.2, 0.4) metre offset. Quick Mirror uses the selection bounds center. Both quick buttons retain their existing boundary-copy policy, unlike the batch panel's default clearing policy; use the batch panel or PWDT for explicit control. Existing IDs are not renumbered and geometry is no longer rounded to a few decimal places during copying.

inspectModelBatch counts selection only; it is not a solver precheck or full operation dry run. A successful changed batch commits one history checkpoint and invalidates the old result observation. No-op edits create no checkpoint. Invalid requests leave model, results and history untouched. Receipts contain selected/affected, added and removed counts, not a duplicate model. Undo/redo restore 3D multi-selection and geometry; they do not roll back backend saves or cancel submitted jobs.

Array limits per operation: 1–1,000 additional copies, at most 100,000 added nodes and 200,000 added members. These are frontend resource limits, not a frame-rate guarantee. Invalid indices, non-finite values, missing materials, unsupported axes, degenerate affected members and excessive allocations fail with stable model_batch:* codes. Await each PWDT invocation: a second batch against an already consumed, not-yet-published model returns model_batch:stale_model rather than overwriting the first edit. The fixed selector contract exposes modelBatchPanel and parameterized modelBatchControl; prefer registered actions over clicks for automation.

Qualification: pure tests include 100k-node selection scans, 200k-node transforms with bounded topology reads, 72 rotation/inverse cases across axes, angles and pivots, exact quarter turns, planar guards, connectivity remapping, immutable snapshots and failure atomicity. Isolated real-browser tests exercise GUI/PWDT parity, explicit transform pivots, copied selection, grid-collapse rejection, save payloads, confirmation invalidation and undo/redo with a mock backend. Edit inside the fullscreen 3D workspace

For truss_3d, enter the existing immersive viewport from its header. The fullscreen element owns the node, batch, quick-property, study and save tools. Model opens batch modeling, Study opens the real study controls, and Save opens project/model storage without leaving fullscreen. Undo and redo stay available across tool tabs. Outside fullscreen, Tools opens Workspace / Tools / Studio.

  • Batch operations use the same validated controller as the sidebar and PWDT. Selection queries, rotation pivots, offsets and other form parameters are shared in an in-memory draft, not copied model snapshots. Closing tools, changing tabs and leaving fullscreen unmount inactive editors but preserve those parameters. A different study kind starts with compatible defaults.
  • Drafts are not autosaves or crash recovery. Page reloads discard them. Destructive deletion confirmation and old success messages never survive editor remounts; confirm again against the current model and selection.
  • Quick properties honor multi-selection before the anchor node: group supports, nudges and loads target the group. The shared edit path records history and clears stale results. Undo restores geometry and selection but does not reverse an already completed backend save.
  • Select matches promotes an all/current/indices/range query, with optional inversion, into actual 3D canvas selection. It includes nodes hidden by render sampling; it does not edit geometry, record history or invalidate results. The form switches to that current selection and clears inversion. Clear selection also clears the anchor, selected member and link draft. PWDT uses selection/query3d; an empty explicit indices list clears selection.
  • Drag the tool/canvas separator, use arrows for 10-pixel steps (Shift: 40), Home/End for limits, or double-click to reset. Width and stacked height are remembered independently in this viewport session only. The dock is capped at 40% of available horizontal space and 45% of stacked vertical space. A cancelled pointer, window blur or resize discards an unfinished drag. Resizing updates CSS through animation frames, not React model snapshots.
  • The field area scrolls independently with batch actions at the bottom. Very short stacked docks scroll the tool as a whole with a sticky batch footer rather than collapsing fields to zero height. View controls are collapsible. The renderer retains its aspect-fit surface so geometry and picking are not stretched out of alignment.
  • Save requires an existing project and a nonblank model name (up to 256 characters). With no saved model selected it creates one; otherwise it saves a new version. Save As creates a separate model. Both invoke the existing model/save/model/saveAs actions with the name in the same request. The fullscreen UI prevents duplicate submissions while busy, even if its tab is closed and reopened; errors retain the name draft for correction and retry. The header Library button exits fullscreen before showing the workspace library, so it cannot silently navigate a hidden sidebar.
  • Storage is not an all-or-nothing distributed transaction: updating model metadata and creating its version are separate existing backend writes. A failed or uncertain request may have partially completed; inspect stored records before retrying an uncertain response. The busy lock is local to this viewport, not a cross-client idempotency mechanism. Project-context guards prevent a late response from replacing a newer workspace selection; a contextChanged receipt refers to the original write, not the current model.

Heat-to-thermo projection boundaries

The Inspector export action and PWDT state/projectHeatToThermo share the same transformation for heat bars, plane triangles, and plane quads. Solve the heat model first, project its full result, review the mechanical model, save, and solve again.

  • Projection requires complete, finite nodal temperatures and a result whose mesh matches the working heat model. Temperature transfer follows node indices, not response array order; missing nodes, ambiguous indices, or mismatched identities are rejected with HEAT_THERMO_PROJECTION_INVALID, not filled with zero.
  • The current heat input must still match the solved input: node and element identities, temperature boundaries, heat loads, conductivity, area or thickness, and material bindings. Changing these values requires a fresh heat solve, even when the mesh is unchanged. Omitted optional temperature and load values are compared as zero; project and version labels are not computational inputs.
  • A failed conversion preserves the source study, active result, and saved-model selection. A successful conversion detaches the new working model from the saved source model and version. The next ordinary save creates a separate model in the same project, rather than overwriting the heat input.
  • Temperature values are copied into temperature_delta using the engine's existing zero-reference convention. No ambient temperature is inferred. If the heat result represents absolute temperature, convert it to the intended temperature difference before using this projection for research.
  • A mechanical seed with matching geometry and connectivity retains its supports, loads, and material properties. Without that seed, the helper supplies defaults, including supports derived from fixed-temperature nodes. These are convenience defaults, not a physical boundary-condition inference. Review constraints, Young's modulus, thermal expansion, loads, and units before solving.
  • The triangle and quad heat-thermo recipes preserve separate saved stages and finish in System / Data / Results for their project. Electrostatic-heat-thermo recipes add the existing electrostatic-to-heat heuristic; this is not a qualified Joule-heating or fully coupled multiphysics solver.

Browser regression tests execute the product GUI and PWDT action bridge with synthetic solver and archive responses. They verify projection, save isolation, resubmission, result navigation, and error preservation. They do not qualify numerical accuracy, actual Pyodide WebAssembly execution, or an installed native WebView.

Electrostatic-to-heat projection boundaries

PWDT state/projectElectrostaticToHeat and the triangle and quad electrostatic-heat-thermo recipes use the same validated transformation. This is a workflow convenience heuristic, not Joule heating: each nodal heat load is the mean incident electric-field magnitude multiplied by a scale, not a conductivity-weighted power-density calculation.

  • The result must contain every source node and element exactly once, with matching identities, coordinates, and connectivity. Output follows the solved input order even when response arrays are shuffled. Potentials must be finite, field magnitudes finite and nonnegative, and source thickness positive. Invalid or incomplete data raises ELECTROSTATIC_HEAT_PROJECTION_INVALID instead of being filled with zero.
  • The current electrostatic model must still match the solved input, including node identities, potential boundaries, charge densities, permittivity, thickness, and material bindings. If it has changed, solve it again before projecting. A rejected projection retains the source study, active result, and saved-model selection.
  • A thermal seed is reused only when geometry and connectivity match, not merely node and element counts. Its thermal constraints, temperatures (including zero), and positive conductivities are preserved. Projected heat loads replace previous seed loads rather than accumulate them. Element thickness comes from the solved electrostatic input.
  • Without a matching seed, defaults are conductivity 45, load scale 50, and boundary temperature range 20..100. Fixed-potential nodes become fixed-temperature nodes; if there are none, potential extrema provide anchors. These are reviewable convenience defaults, not physical boundary-condition inference. PWDT recipes currently use these defaults rather than exposing projection options.
  • The projection helper rejects nonfinite option values, nonpositive conductivity, negative load scale, reversed temperature ranges, and arithmetic overflow. Explicit zero load scale and a uniform temperature range remain valid. Incident-load averaging avoids overflowing an intermediate sum of otherwise finite nonnegative values.
  • Material bindings carry cloned definitions from their actual source: an explicit thermal seed binding uses its seed library; otherwise the electrostatic input supplies the binding. Missing references, duplicate identifiers, and conflicting definitions under the same selected identifier are rejected.
  • Successful projection detaches the working copy from its saved source, so the next save creates a separate heat model. A failed recipe stops before the heat-stage save or submission. Inspect the retained source and error, obtain a fresh result, and continue the individual stages; restarting a whole recipe may create new records and is not automatic rollback.

Unit and browser tests cover response ordering, invalid payloads, material provenance, arithmetic boundaries, source preservation, and a fresh-solve retry. Browser solver responses are synthetic; these tests do not qualify physical coupling accuracy, installed native WebViews, or Pyodide WebAssembly execution.

Waiting and failure rules

  • Await every state-changing action. The Workbench action bridge waits for the UI state commit before resolving, so the next action uses the updated project, model, selection, and parameters.
  • Wait on observable state with wait_for_job_done, wait_for_message, or wait_until; do not add arbitrary sleeps around network work.
  • wait_for_job_done reports any terminal state, including failure or cancellation. run_current_study requires success and raises on failure instead. All five built-in recipes enforce this at every stage, before projection, another save, or opening results. They do not automatically retry a solver submission; completed input saves remain available for inspection.
  • ky.state()["hasResult"] is a boolean for the recognized active result, including two-dimensional heat and electrostatic results. It is not a count of archived results and is cleared when switching to another study. Clearing the current view does not cancel backend jobs or delete archived records.
  • Use sleep only for bounded UI settling where no stronger state exists.
  • High-risk actions still require product confirmation. PWDT does not create hidden authority.
  • If an action is absent, stop and inspect the parity report instead of clicking a similarly named element.
  • If a run fails, preserve the action log and current snapshot before replaying any step.

Runtime loading recovery

  • If the Pyodide script download or initialization fails, inspect the runtime error and use Load runtime again. Reloading the page is not required, and the editor source is preserved.
  • The script download has a 30-second timeout. Failed script tags and failed initialization promises are discarded so that a new explicit attempt can proceed; simultaneous loaders share one attempt.
  • A Python script error does not discard a successfully initialized runtime. Fix the script and run it again; earlier GUI actions or backend writes are not rolled back automatically.

Recovery tests use intercepted script downloads and a runtime adapter. They verify the GUI loading and retry path, not an actual Pyodide WebAssembly download or Python numerical execution.

Concurrent project operations

  • Model and version loads use the latest workspace operation. A late response cannot replace a newer load or a different selected project; stale failures do not overwrite that workspace's message.
  • A save already sent to the backend still belongs to its original project and model. If the workspace changes before the response is applied, the save action returns its persisted ID with ok: true and contextChanged: true, without selecting the old model again. Inspect the original project before retrying; do not assume that the write failed.
  • Project creation, update and deletion, saved-model deletion, and version rename and deletion follow the same rule in GUI and PWDT. Completed stale writes return the original affected ID with contextChanged: true; they do not select another project, reset its drafts, or replace its feedback. Failed writes still reject rather than report success.
  • Deletion reconciles associations by resource identity: deleting the active project detaches its project, model, and version; deleting the active model detaches that model and version; deleting a version detaches only that version. This also applies if you switched to another version within the deleted project or model. The working model remains available, but saving a detached copy cannot silently overwrite a different saved model. An unrelated selected resource remains untouched.
  • Completion checks cover the final version-list refresh as well as the initial write or load. Switching away and back still invalidates the operation; committing its own newly saved or loaded selection does not.
  • Built-in macros, run_steps, and all five built-in research recipes stop remaining steps when an action reports contextChanged. This applies to both browser PWDT and Python PWDT, including project creation and each intermediate save in composite recipes. The completed write is retained; inspect it before retrying rather than generating duplicates. Superseded loads fail with WORKBENCH_CONTEXT_CHANGED.
  • Direct invoke and save_model callers still receive the affected ID and completion flag. Check contextChanged before continuing a dependent action. ensure_project stops with an error if a newly created project could not become the active workspace, rather than silently continuing in another project.
  • A bundle import that has begun creating records finishes in its new project, but does not replace a workspace selected while the import was pending. The imported project remains available in the refreshed library.
  • Catalog refresh preserves newer selection. It does not load model geometry, so it never attaches an unbound working model to the first saved model; open that saved model explicitly instead. If refreshing fails, the last usable catalog remains visible with runtime recovery feedback; this does not claim the cached catalog is current.
  • save_model(name=..., material=...) passes metadata in the checkpoint request, not in a preceding workspace edit. A rejected save leaves the working name/material unchanged; a successful current-context save publishes them and stores matching payload metadata. Saving an existing model uses one backend checkpoint operation for metadata, geometry and version creation, without a preliminary PATCH.
  • A failed version-list read retains known versions only for the same selected model, with a model_versions recovery issue. Use the recovery refresh control or runtime/refreshAll to retry the read; do not repeat a successful save just to refresh history. Navigation invalidates delayed responses and hides the previous model's rows.

These boundaries are exercised by isolated browser tests with delayed and failed API responses. The shipped Python prelude is also executed against an in-memory JavaScript bridge adapter, not just inspected as text. That frontend test requires Python 3 (CI uses 3.12); it does not add a native Python dependency to the application. These checks do not qualify Pyodide downloads or WebAssembly startup, packaged WebViews, real database transactions, or numerical solver accuracy.

Recovering an uncertain checkpoint write

GUI Save/Save As and PWDT share the checkpoint retry service. During the current WebView session, retrying unchanged content after a lost response reuses the request ID. Concurrent identical submissions share one in-flight write. A valid success receipt completes that attempt; a later intentional save then receives a new ID. A malformed success response does not complete the attempt.

The retry key is scoped to the backend, authentication context, operation, parent and request content. Only digests and request IDs are retained, not credentials or mesh copies. The bounded cache holds up to 64 unresolved requests and refuses new ones rather than silently forgetting uncertain writes. It requires WebCrypto in an HTTPS/localhost context. There is no background write retry or persistent browser draft archive.

# Keep this identifier with your own research-run receipt if the WebView may close.
# Reuse it only with the same project, operation, name/material and model payload.
saved = await ky.save_model(
    name="Tetrahedron trial 01",
    save_as=True,
    request_id="research-run-001-checkpoint-01",
)
if saved.get("contextChanged"):
    raise RuntimeError("Saved in the original project; inspect it before continuing")

The browser helper uses saveModel({requestId: ...}); direct actions and the model/version POST APIs accept request_id. IDs contain 16-128 ASCII letters, digits, underscores or hyphens. The backend commits a small durable receipt with the model or version. Reusing a key with different normalized content returns HTTP 409 checkpoint_request_conflict. Deleting the saved result leaves a tombstone receipt until project deletion; an old retry returns checkpoint_result_deleted instead of recreating it. Replay never rewinds a newer latest-version pointer.

This requires the matching checkpoint-capable backend and database data revision 2; older services may ignore the optional field. The automatic frontend cache does not survive closing or reloading the WebView. After losing that cache, reuse an explicitly retained request ID with unchanged input, or inspect history before saving again. This is bounded retry idempotency, not an exactly-once distributed workflow guarantee.

Undo, redo, and saved-model ownership

Inspector History and PWDT history/undo and history/redo restore the working content, not a database transaction. A saved model or submitted job is not deleted or rolled back by restoring a snapshot.

  • Restoring within the same project, saved model, and study keeps the current save binding. Even if another version has been saved since the snapshot, the next ordinary save appends a version to that model rather than creating a duplicate.
  • A snapshot from another model, project, or study is restored as a detached working copy in the current project. The next ordinary save creates a separate model. Missing snapshot provenance is also detached; restoration never selects an old project or resurrects a deleted record.
  • For example, after saving a projected thermo model, undoing back to its heat source cannot save heat content over the thermo record. Redo restores the working thermo content, not permission to overwrite its former saved record.
  • Every restore invalidates earlier pending model loads and saves, including when the binding stays the same. A completed save can still return its persisted ID with contextChanged: true, but cannot replace the restored selection, geometry, or feedback. Inspect the original saved record before retrying.
  • Restoration clears the active result and job view and invalidates earlier run submissions, polling, and completion observations. Late responses cannot replace the restored view or let a dependent recipe continue as if it still owned the result. This does not cancel a backend job; inspect Job and Result records separately. Solve the restored input again before projecting it.

Snapshots retain only a small project/model provenance record for these checks. Immutable model geometry remains shared rather than deeply copied, and the history capacity is unchanged. Browser regressions exercise both GUI and PWDT paths with synthetic API responses, not native solver accuracy or installed WebView qualification.

Reopening jobs and cancelling observations

  • Library / Jobs and Results reopen persisted jobs through the same history action. A supported simulation result is routed to exactly one of the 23 built-in Workbench study types using its input dimension, connectivity, and constitutive fields. Heat, electrostatic, and thermo-mechanical results must not fall through to a mechanical study merely because they share node arrays or stress summaries.
  • Opening a solved input creates a detached working copy in the current project. Its old project/version labels are not carried into new submissions. The next ordinary save creates a new model; use the separate linked-version action when you intentionally want to resume a saved version. Archived inline material values and material libraries are retained, not replaced by the current material preset.
  • Unsupported or structurally ambiguous simulation results fail with HISTORY_RESULT_INVALID before replacing the current model or active result. Opening a job without a result clears the previous result view but keeps working geometry and save binding. Workflow graph results still open the workflow run trace rather than a simulation model.
  • Reading history does not stop an active submission or polling loop. The observation changes only after the archive response passes identity, study-shape, and summary preparation checks. A network or invalid-archive failure keeps the original computation observable; retrying the history read does not submit another computation.
  • A newer history open, run, workspace load, or undo supersedes an older pending history response. A stale success or error cannot overwrite the newer view. Opening history is not a backend rerun, and undo does not delete the archived job.
  • job/cancel keeps observing the active job until a valid cancelled response confirms cancellation, so a rejected cancellation remains retryable. HTTP success alone is insufficient: the backend may return an already completed or failed job. Those replies stop dependent steps with JOB_CANCELLATION_NOT_CONFIRMED; invalid lifecycle/progress details produce JOB_CANCELLATION_INVALID. The existing observation remains active to retrieve the actual job outcome.
  • Confirmed cancellation clears the current result preview without deleting archived records. If the user has opened another job or restored a snapshot meanwhile, the receipt returns the original jobId with contextChanged: true; it cannot stop the newer observation, clear its result, or replace its feedback. Dependent action sequences stop at that flag. This receipt confirms the control-plane status, not an independent attestation of physical worker termination.
  • Overlapping frontend cancellation calls for the same job share one in-flight request and receipt, including the post-confirmation history refresh. Once it settles, an explicit retry is allowed for an active job; the controller does not automatically retry cancellation writes. A history-refresh failure after confirmation cannot turn the accepted cancellation into a failed operation.
  • Failed or malformed job-history refreshes retain the last validated catalog and selection, with a job_history issue in the existing recovery surface. Inspect it from Library / Jobs or System / Runtime / Watchdog. Both the recovery card's refresh button and runtime/refreshAll refresh job history. JOB_HISTORY_INVALID rejects malformed lists and duplicate/invalid records before publication. A successful empty list is authoritative and clears the catalog; a successful refresh clears only its own recovery issue.
  • If cancellation commits while a history read is still pending, that read is superseded rather than restoring an observation changed by cancellation. Reopen the archive explicitly if needed. Conversely, cancellation of the old job cannot overwrite a history view that has already committed.
  • Polling checks the response job ID before applying any job or result frame and retries reads within the existing three-consecutive-error budget, never by resubmitting the computation. A completed job with a missing or null result is not a successful run, for either orchestrated or direct-mesh execution. A result-free terminal poll clears any earlier progress preview. runSteps and built-in research recipes stop before dependent saves, projections, or submissions; a new computation requires an explicit invocation.

These checks exercise archive routing and GUI/PWDT state ownership with synthetic API responses. They do not certify solver accuracy, arbitrary advanced result formats, actual Pyodide execution, or a packaged WebView.

Stable selector escape hatch

Prefer actions and recipes. When a read-only UI assertion truly needs a selector, resolve it through the product UI contract instead of writing a CSS selector tied to layout or translated copy. 

selector = ky.ui_selector("runtimeTab", "control")
panel = ky.query_selector("runtimePanel")
tabs = ky.query_selector_all("runtimeTab", "overview")

Completion contract

  • The script checks capabilities before mutation.
  • The same project, model, terminal run, and result exist as in the manual tutorial.
  • No localized copy, layout class, or raw DOM path is used as an action contract.
  • The action timeline identifies the failing action if the loop does not complete.
  • Project bundle exports include only jobs explicitly assigned to the selected project. Other projects and unassigned runtime jobs are not included.
  • Switching to another existing project detaches the current saved-model and version IDs, while keeping the working geometry available to save into the new project. Unknown project IDs fail without changing the active context.
  • Bundle import validates the file sections and active workspace payload before creating records. Model and version IDs are remapped to the imported project; the workspace name and selected older version are retained, so the next save continues that model instead of duplicating it.
  • If an expected result is unavailable or mismatched, export returns partial: true and the GUI shows the existing partial-export warning. Keep the available data and retry after the service recovers.
