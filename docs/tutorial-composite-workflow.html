Tutorial 02 · Workflow Builder

Turn operators into one traceable flow

Start from a known catalog flow, inspect its graph and dataset contract, then create a bounded local variant. The goal is not graph size; it is a complete solve -> bridge -> solve -> extract/export chain with lineage.

Surface: Workbench Workflow Contract: graph + dataset Evidence: run record + exports
Tutorial center Graph contract Dataset contract

Prerequisite

Finish the first GUI loop and keep one active project. A workflow run must have a project owner, and a local draft must not silently attach to whichever project happens to be selected later.

Step 1

Prove the catalog path first

  1. Open Workflow -> Catalog and refresh the catalog.
  2. Filter for a healthy built-in heat/thermo or electrostatic/heat workflow.
  3. Run the reference sample without modifying it.
  4. Open Workflow -> Runs and confirm node progress, terminal status, and exported summary.

Checkpoint: the catalog id, workflow run id, current/terminal node, and output artifact are all visible before authoring starts.

Step 2

Open a local graph variant

  1. Open the selected catalog entry in Builder.
  2. Duplicate or promote it to a local workflow instead of editing the built-in source.
  3. Name the variant tutorial-heat-thermo-v1.
  4. Inspect node ids, operator ids, ports, edges, entry inputs, and output artifacts before changing topology.

A workflow node describes an operator task. The executable engine contract remains TaskIR/runtime-protocol based; the UI graph and any Elixir description layer do not become the solver implementation.

Step 3

Build one cross-operator contract

  1. Insert the known heat -> bridge -> thermo chain, or its electrostatic -> heat -> thermo counterpart.
  2. Keep solve outputs and bridge inputs typed. Do not connect ports only because their JSON happens to look similar.
  3. Declare dataset values with stable ids, types, units, provenance, and producer/consumer ownership.
  4. Declare at least one output artifact and bind it to the final extract or export node.

Checkpoint: every edge resolves existing ports, every required input has one source, and the dataset contract has no orphan producer or consumer.

Step 4

Validate before running

  1. Open Consistency check and review all graph and dataset diagnostics.
  2. Preview automatic fixes before applying them. Retain the correction snapshot.
  3. Resolve manual-review items explicitly; do not treat “no auto-fix” as “safe”.
  4. Run the current draft only when validation reports no unresolved contract error.

The builder keeps correction snapshots for recovery, but summary-only snapshots cannot restore a complete draft. Verify the snapshot type before relying on it.

Step 5

Inspect lineage and export the right thing

  1. Use Runs to inspect each node status and the bridge-alignment diagnostics.
  2. Export Graph JSON and Dataset JSON as inspectable workflow contracts.
  3. Export a workflow template/package only when the reusable topology and install rules are intentional.
  4. Use KCore for the portable research/result artifact, not as a replacement for the editable workflow project.
./scripts/kyuubiki kcore export schemas/examples.kcore-export.json --out tmp/tutorial-result.kcore
./scripts/kyuubiki kcore inspect tmp/tutorial-result.kcore
./scripts/kyuubiki kcore verify tmp/tutorial-result.kcore

Completion contract

  • The local variant has its own id and still names its catalog origin.
  • Graph and dataset validation complete without unresolved contract errors.
  • The run record exposes node-level progress and a terminal workflow state.
  • At least one output artifact resolves back to its producing node and source inputs.
  • Graph JSON, Dataset JSON, and any KCore artifact pass their respective validators.
