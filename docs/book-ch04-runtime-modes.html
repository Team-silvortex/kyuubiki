Runtime and deployment modes

The product is intentionally deployable in multiple shapes, but those shapes must stay explicit and understandable so operators and runtime engineers know which contracts apply.

Back to book Previous chapter Next chapter

Deployment shapes

  • local workstation: frontend + orchestrator + local Rust agents.
  • cloud control plane: browser and orchestrator with remote persistence and external agents.
  • distributed control plane: separated control plane with remotely deployed solver nodes.
  • headless peer mesh: future or selective mode where Rust agents can cluster without GUI or Phoenix on the hot path.

Single-Agent direct execution and recovery

The native frontend gateway can bypass Orchestra for direct solving. A Workbench direct-mode run with exactly one endpoint now uses the durable contract. This is not a claim that all Workbench workflows run without Orchestra. Existing /api/direct-mesh/solve results still use a process-local cache.

  • Configure KYUUBIKI_AGENT_EXECUTION_STORE to a dedicated, absolute directory in the deployment's writable state. Its parent must already exist. The Agent creates the final directory; Unix permissions must be owner-only. One Agent process holds its exclusive directory lock. No implicit home-directory store or memory fallback is created.
  • The desktop-managed runtime now provisions a separate agent-executions/agent-<port> under its writable state on Agent startup. Override the parent with KYUUBIKI_AGENT_EXECUTION_STORE_ROOT, an absolute directory. Runtime status displays the root and the Agent descriptor displays the concrete directory and limits. Managed startup rejects the standalone single-directory override to prevent multiple Agents sharing one ledger. Already-running Agents need an explicit managed restart to receive this configuration.
  • run_durable_agent_task accepts a caller-generated execution_id (32 lowercase hex characters), a solver RPC method, and object params. Execute-mode run_operator_task_ir also uses this boundary. The Agent writes and syncs the admission before dispatch, and the checksummed final receipt before returning. The engine and operator implementations stay unchanged.
  • submit_durable_agent_task accepts the same task but returns after reserving an execution slot and syncing admission, without waiting for computation. Its worker has no submitting socket, so losing that connection does not cancel the task. Existing capacity, drain, watchdog and exact cancellation rules still apply. The slot stays owned through receipt commit; no unbounded background queue is introduced.
  • fetch_durable_agent_execution queries that exact ID. States are not_found, running, completed, failed, or outcome_unknown. Completed/failed records contain the original nested RPC response. An interrupted admission without a receipt is unknown, not proof of failure before execution. No state grants automatic replay permission.
  • Persist the chosen Agent and execution ID on the caller side before submitting. Repeat IDs with identical inputs return the existing state or receipt; changed inputs are rejected. Retry only against the same Agent with the same preserved store. Replacing or deleting that store removes its deduplication history. These IDs are not authentication credentials.
  • list_durable_agent_executions takes limit (1 to 64) and optional after (execution ID). It reads only admission metadata, not result receipts; IDs sort lexicographically, not chronologically. next_cursor is the final ID when another page exists. This is not a snapshot across pages; refresh from the first page to include newly admitted IDs that sort before the cursor. An index row is not evidence of successful or completed computation.
  • cancel_durable_agent_execution requires the inspected execution_id, process_instance_id and request_digest. It can mark only the original live async owner, never a later task reusing a job or transport request ID. Its requested receipt explicitly has execution_terminal_confirmed: false. Query again to observe the persisted final result. This control neither replays work nor creates pending cancellation for a future execution; synchronous wrappers have no async owner and are not cancelled through this convenience control.
  • The Rust HTTP gateway exposes POST /api/direct-mesh/tasks with execution_id, study_kind, input, and a single allowlisted endpoints entry. Query via POST /api/direct-mesh/tasks/inspect with the same endpoint and ID. Responses expose execution and endpoint. Submission uses asynchronous admission, while inspection reads the Agent ledger rather than the gateway's in-memory result cache. Unknown transport outcomes preserve this handle and never trigger cross-Agent failover. An HTTP 200 alone does not mean computation succeeded: inspect execution.status and the nested response.
  • The native gateway also exposes POST /api/direct-mesh/tasks/list and POST /api/direct-mesh/tasks/cancel, carrying the corresponding RPC fields plus one allowlisted endpoints entry. Both enforce the same gateway token and return a validated recovery envelope. Neither route uses Orchestra history or the gateway result cache.
  • The frontend runtime client exposes submitDurableDirectStudy and inspectDurableDirectExecution. Its recovery helper saves a caller-owned handle before sending, pins gateway and Agent, and only inspects after reconnect. Handle storage failure blocks submission; connection changes fence late responses. The ordinary run button and PWDT job/run use this service for exactly one declared Agent. They check its durable capability before reserving a local identity; disabled/old Agents fail closed, without a synchronous fallback. Multi-Agent selection still uses its existing synchronous route and has not acquired this recovery guarantee.
  • Before dispatch, the Workbench stores only the execution ID, endpoint, study kind, gateway-address digest and creation time. Desktop uses the native desktop-direct-execution.json journal; normal browsers use kyuubiki-direct-execution IndexedDB with strict durability requested. Desktop host failure never falls back to browser storage. There is no RAM fallback, model copy or token persisted. Limits are 64 pending identities and 64 KiB for the native journal; one pending reservation per gateway/Agent blocks duplicate runs across views. Browser storage remains subject to browser/user eviction.
  • In direct mode, open Workbench System > Runtime > Direct Execution Recovery. The panel is collapsed and performs no reads until requested. It lists 24 admissions per page, inspects one receipt, and asks for confirmation before cancellation. GUI and PWDT share directExecution/pending, directExecution/list, directExecution/inspect, and directExecution/cancel. Inspection returns bounded status/identity metadata to action history, not numerical result arrays. It does not replace the current model or result. Unknown, not-found and transport failures never authorize resubmission. Ordinary synchronous solves do not appear in this ledger. Use Local Pending Executions after a lost response or UI restart. Inspecting a matching terminal receipt clears only that caller reservation, not the Agent receipt. Unknown/not-found records remain pending. Ordinary cancel routes the current direct handle to its original Agent, never an Orchestra job ID; cancellation registration does not clear observation or mark the job cancelled. Automatic observation is bounded to 40 inspection reads.
  • The ledger stores at most 1,024 admissions, 8 MiB per encoded receipt, and 128 MiB of retained record bytes, with capacity reserved for active receipts. It keeps no model-input copies or backup generations. Capacity exhaustion rejects new work instead of silently evicting identities. Clear a disposable ledger only with the Agent stopped and callers retired.

Qualification includes real local Agent process kills before computation, after durable receipt sync but before reply delivery, and after completion, with repeat restart and duplicate-submission checks. This is not physical power-loss qualification or a claim of mid-solver numerical continuation. Installed-WebView-to-real-Agent qualification, multi-Agent durable selection, full workflow-graph execution and TLS/authentication parity remain separate work. The direct transport still requires a trusted network boundary; do not expose the raw Agent listener publicly. See the scoped test report. The asynchronous admission report records the detached-worker, shutdown and frontend recovery-interface checks. The recovery controls report tracks the separate Agent index, exact-owner cancellation and GUI/PWDT checks. The default-run report adds native caller process-kill, browser reload and ordinary run/cancel coverage.

Operational goal

Each deployment mode should remain legible in terms of storage, discovery, authority, and update behavior. Documentation should make those tradeoffs visible instead of hiding them in environment files.

Local background-service lifecycle

Hub, Workbench, Installer, and the native runtime command share one Rust lifecycle implementation. The GUI is a control client, not the lifetime owner of computations: closing a window or quitting the GUI does not stop background services. Start, stop, and restart remain explicit actions. There is no implicit OS-login startup or automatic crash-restart policy.

  • Start: validate the requested ports and existing ownership, then start local agents, Orchestra, and the optional frontend gateway. A repeated start reuses only verified, listening service instances.
  • Start failure: detect an early process exit without waiting for the full readiness timeout; terminate a child whose registration or readiness fails, and roll back only services created by this operation. Existing services are preserved and cleanup failures are reported.
  • Stop: stop the frontend gateway, Orchestra, and local agents in reverse startup order. A failure on one service does not skip cleanup of the other owned services or produce a false success.
  • Restart: hold the same OS-backed lifecycle lock across stop and start. A competing mutation fails as busy; status remains readable. A controller crash releases the lock without deleting its lock file.
  • Recovery: a later controller can inspect and stop registered background processes left by an interrupted launcher. Dead PID records are reconciled. Unverified live processes and inconsistent records fail closed.

Readiness here means a live, ownership-verified process and a listening local port, not proof of API health, solver correctness, or completion of in-flight research. Stop is an explicit service shutdown, not a job-draining contract; checkpoint or complete important tasks before stopping the stack.

Visible state, scope, and ownership

Installed payloads remain separate from writable state. Use KYUUBIKI_RUNTIME_ROOT for the installed payload and KYUUBIKI_RUNTIME_STATE_ROOT for its external writable state. Status reports the resolved runtime paths, lifecycle policy, lock location, and service readiness. Source mode uses the repository's tmp/run.

  • <runtime-state>/run/lifecycle.lock is a persistent, small OS-lock file, not a stale-lock marker to delete manually.
  • Each managed service has a PID file and a *.process.json ownership record with schema kyuubiki.runtime-process/v1, process incarnation, label, port, and canonical state-directory identity. It stores no launch environment, credentials, or command-line secrets.
  • PID reuse, a copied record from another state directory, or a live legacy PID without an ownership record never authorizes automatic adoption or termination. An occupied unmanaged port is blocked, not a healthy running service.
  • KYUUBIKI_ORCHESTRATOR_PORT and KYUUBIKI_FRONTEND_PORT select validated nonzero ports; defaults are 4000 and 3000. Nondefault ports have distinct PID and log filenames. Local agent ports come from the configured discovery source.
  • KYUUBIKI_RUNTIME_ORCHESTRATOR_ONLY limits mutations to Orchestra; KYUUBIKI_RUNTIME_FRONTEND_DISABLED excludes the frontend gateway. Distributed mode does not start or stop local agents. Use consistent scope settings across start, status, and stop.

During an upgrade from legacy PID-only management, stop old services with their existing controller before switching controllers. Do not fabricate ownership records or delete live PID files to force adoption. An interrupted registration with inconsistent files requires diagnosis, not blind cleanup. OS service registration, task draining, and supervised restart with backoff are separate follow-up work, not guarantees of this lifecycle layer.

Lifecycle regression tests

The native tests use temporary payload/state directories, dynamic ports, and a Rust listener, without Node, shell launch scripts, database services, or the workstation's default service ports. The same scenarios run on macOS and Linux; Windows-specific paths also receive compilation checks. These fixtures validate process management, not the full production stack. 

cargo test --locked --manifest-path workers/rust/Cargo.toml -p kyuubiki-platform -p kyuubiki-desktop-runtime

Remote deployment maturity

Installer remote deployment is currently a policy-bounded SSH pilot, not yet a full production deployment service. The roadmap is to move toward explicit deployment plans, durable journals, artifact delivery, host trust, and physical/containerized remote tests. The first structured plan preview now lives in the Installer CLI as remote-deployment-plan, with matching journal preview records available through remote-deployment-journal and artifact delivery preview through remote-artifacts.
