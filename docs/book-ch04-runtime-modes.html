Runtime and deployment modes

The product is intentionally deployable in multiple shapes, but those shapes must stay explicit and understandable so operators and runtime engineers know which contracts apply.

Back to book Previous chapter Next chapter

Deployment shapes

  • local workstation: frontend + orchestrator + local Rust agents.
  • cloud control plane: browser and orchestrator with remote persistence and external agents.
  • distributed control plane: separated control plane with remotely deployed solver nodes.
  • headless LAN peer mesh: explicit-seed discovery and direct Rust Agent execution without GUI or Orchestra. Distributed workflow recovery is not implied.

LAN Mesh: decentralized Agents

Each node owns its native engine and, when configured, its own durable execution store. Discovery is an Agent control-layer concern, not an operator or solver implementation. No Orchestra, Phoenix, Node runtime, elected master or shared execution directory is required. This is explicit-seed gossip, not multicast discovery or an autonomous distributed workflow scheduler.

  • Start each Agent with the same --cluster-id and at least one --peer host:port. Use mutually reachable LAN addresses or local DNS names, not another machine's loopback address. Configure the listener and --advertise-host for that network. Each machine needs its own writable execution-store directory and network access rules. Installer remains the deployment/lifecycle owner; discovery does not install software.
  • --peer and an Orchestra URL are mutually exclusive. Startup rejects mixed authority before opening a ledger. A peer descriptor must match the exact cluster ID (including absent versus configured IDs), report peer_mesh/offline_mesh, and have no Orchestra binding or session. An incompatible seed cannot introduce further peers.
  • Before updating health or merging hints, discovery requires the solver_agent role, the current kyuubiki.solver-rpc/v1 protocol/version, TCP/JSON with length_prefixed_u32 framing, and an advertised describe_agent method. Missing framing or contradictory transport metadata fails the probe even when a reply arrived over TCP. The read-only descriptor_contract exposes these requirements. A busy or draining Agent remains discoverable; matching engine brands, identical solver inventories and new-work admission are not required. discovery_is_execution_readiness=false: compatibility and reachability do not authenticate a node or authorize execution.
  • The read-only describe_agent.peer_discovery policy reports kyuubiki.agent-peer-discovery/v1. At most 64 candidates are retained; each round probes at most eight in rotation. Each query has a 1,500-ms total DNS/connect/write/read budget and a 1-MiB response-frame cap. At most two unresolved DNS workers can remain outstanding. Late DNS results cannot connect. The configured interval is clamped to 1,000-300,000 ms, and stopping the discovery loop interrupts its interval sleep.
  • At most two direct probes run concurrently, with no overlapping rounds. The coordinator publishes each completed compatible response or failure without waiting for other probes in the round. The read-only policy exposes max_concurrent_probes and state_publication=after_each_probe_completion. If a worker cannot start, the remaining worker drains the bounded queue; if neither starts, probing falls back to bounded serial requests. Shutdown stops starting queued probes, discards results after observing the stop, and joins in-flight probe workers within their existing request deadlines. System DNS lookups remain separately bounded and cannot be cancelled.
  • Probe order is a bounded FIFO, separate from the sorted display list. Selected addresses move to the tail; newly learned or readmitted candidates join the tail without overtaking waiting peers. Retirement removes only the retired address from the queue. A continuously retained peer is selected within at most eight complete running rounds, even while membership changes. The read-only policy exposes probe_order, max_probe_rounds_for_retained_peer and probe_round_bound_scope. This is not a wall-clock freshness guarantee: connection deadlines and the configured interval still apply. Concurrent completion/publication order can differ from selection order; two slow probes can still delay candidates waiting behind them.
  • Unprobed seeds are not healthy. Advertised peers are hints, not health evidence or permission to execute. Only a compatible direct response marks a peer healthy; failures degrade it without changing the local authority. cluster_size means self plus known candidates, not a live quorum. Discovery state is process-local and rebuilt from seeds after restart. The health score describes retained candidates, not complete cluster availability or task recoverability; removing a failed hint can increase it.
  • Configured seeds remain until reconfiguration. A learned candidate is retired after three consecutive failed direct probes, followed by a 60-second monotonic cooldown. Neighbor hints cannot reset failures or bypass the cooldown. On re-admission it starts unprobed and needs a new compatible response. The cooldown table holds at most 128 addresses; when full, further failed candidates stay visible until a cooldown slot expires. These limits are read-only fields of peer_discovery. Retirement changes only discovery metadata, never task records, ownership or replay permission. Full configured-seed lists and sustained churn can still delay new discovery; this is not large-cluster qualification.
  • Choose an execution owner before submitting a durable task. Persist the original endpoint, execution ID, persistent store_id and returned identity for inspection and cancellation. IDs and receipts are Agent-local, not a globally replicated ledger. A restarted interrupted execution remains outcome_unknown; peer loss does not authorize resubmitting it to another Agent. Cancelling with a different Agent's process identity is rejected.
  • An address is not an Agent identity: DHCP, port reuse or reinstall can put a different ledger at the same endpoint. Pin the descriptor's durable_execution.store_id before dispatch and send expected_store_id on submit, inspect, list and cancel. A mismatch is rejected before admission, duplicate lookup or cancellation. Reopening the original store preserves its identity; creating a new store does not. Native gateways and guarded clients also reject missing or foreign echoes.
  • The older /api/direct-mesh/solve route selects an eligible Agent using fresh read-only discovery for each new task, then dispatches once. Both first_reachable and healthiest require the current solver RPC protocol, the requested method, an explicit valid accepting lifecycle and configured available execution capacity. Missing metadata is not silently treated as ready. Health only ranks eligible candidates. If none qualifies, the gateway reports rejection reasons and sends no solver request. A missing reply or solver error cannot trigger cross-Agent retry, and failed discovery cannot trigger blind dispatch. It still has a process-local result cache, not a durable receipt. For restart-safe records use the pinned /api/direct-mesh/tasks contract.
  • The read-only kyuubiki.direct-mesh-selection/v1 policy appears as selection_policy in discovery and solve errors, and as direct_mesh.selection_policy on solve success. Lifecycle and admission counts are sampled separately, so the larger count is used. Discovery does not reserve a slot: the Agent still makes the final atomic admission decision. Eligibility is not authentication or recovery proof. Pinned durable inspection, listing and cancellation do not reselect an owner or require new-work eligibility; busy/draining owners can still expose original uncertain receipts while ingress remains available.
  • The native gateway publishes kyuubiki.direct-mesh-transport/v1 in discovery's transport_policy and solve responses' direct_mesh.transport_policy. Describe, async submit, receipt lookup, index and cancellation share a 15-second total exchange budget, including DNS capacity wait, resolution, connection, writes and reads. Partial headers or payloads cannot renew it. These control methods reject progress frames and malformed, contradictory or wrong-version RPC replies.
  • Gateway DNS has at most four outstanding workers. Waiting callers share their existing deadline, and timed-out DNS workers keep their slots until they actually finish; late resolution cannot connect. At most eight resolved addresses are considered, each with at most 500 ms to connect. Reply frames are limited to 1 MiB for metadata, 9 MiB for durable submit/ receipt lookup, and 64 MiB for legacy solver results. These are encoded limits, not a claim of identical process heap usage.
  • Legacy solves retain a 15-second deadline per complete frame rather than the control operation's total deadline, so normal long-running solves can continue with valid progress. Only the newest 128 progress frames and at most 1 MiB of normalized encoded progress are retained; earlier telemetry is dropped. The final solver result is not truncated. Continuous valid heartbeats can still keep a legacy solve open; this is not a whole-job deadline or proof of numerical progress. Transport failure never authorizes cancellation confirmation, caller-journal cleanup or cross-Agent replay.

Local tests run three real Rust Agent processes in a ring, execute bar solves, forcibly terminate one owner, verify that the other two continue, and rejoin the original owner without replaying its uncertain work. Separate tests cover foreign-cluster hints, cancellation identity, same-address ledger replacement and bounded shutdown. This is loopback multi-process evidence, not physical multi-host, power-loss or authenticated-LAN qualification. A cluster name is not authentication: the raw Agent listener still requires a trusted network boundary. Cross-node workflow journaling, ownership transfer and network-partition handling remain separate work; peer discovery alone does not provide those guarantees.

Native Agent request admission

Native TCP connections now default to host loopback only, including when the Agent binds to 0.0.0.0. This applies equally to standalone, Orchestra-bound and decentralized Mesh modes. Before upgrading a LAN deployment, explicitly configure its permitted caller addresses; changing the bind address, declaring a cluster, or supplying certificate metadata does not grant remote access.

  • KYUUBIKI_AGENT_ALLOWED_PEER_IPS adds up to 64 comma-separated unicast IPv4/IPv6 literals to the always-permitted loopback addresses. Unset means loopback only; an empty value, hostname, port, wildcard, subnet, multicast or unspecified address rejects startup. The input limit is 4096 bytes. IPv4-mapped IPv6 addresses are canonicalized. There is no DNS expansion or automatic trust of discovered peers.
  • Configure this in the Agent service's host-owned environment, not in a project bundle, task or source-controlled server configuration. Permit the actual socket source of the controller/gateway and each intended Mesh peer. The systemd template reads its existing deploy/kyuubiki-agent.env; no actual host addresses are embedded in the template. Every peer applies its own policy.
  • The kernel socket peer address is checked before connection permits, handler threads, request frames or recovery-reserve admission. Unknown peer addresses and unlisted non-loopback sources are closed without reading or replying. Rejections increment a bounded counter instead of producing one log line per connection.
  • describe_agent.request_ingress.network_access and the registration/heartbeat payload expose kyuubiki.agent-network-access/v1, effective addresses, rejection count and limitations. Changes, including removal of an allowed address, take effect on process restart, not hot reload. Drain/reconcile existing work before a planned restart; access-policy changes do not authorize replay of uncertain executions.
  • Agent startup, Installer environment validation and managed-runtime preflight use the same pure policy parser. Before a managed restart stops existing services, it validates and captures the target startup environment. An invalid local Agent policy is rejected without stopping the existing services or replacing their execution records. Modes that do not launch a local Agent do not require this policy to be valid.
  • Runtime status reports agent-network-config as configured intent, with running-policy=not-observed, not proof that an already-running Agent applied it. Inspect the Agent description for its effective policy. An invalid network setting still permits status inspection and explicit stop; fixing it does not silently restart work. This preflight does not make arbitrary launch failures transactional.

This is source-IP containment, not authentication, encryption, user identity or single-Orchestra authorization. Local processes still share loopback trust, and proxies/NAT are identified by their observed socket address, not the original caller. Explicit permission does not grant remote drain/resume authority. Keep an isolated trusted network boundary; native identity verification, credential revocation and authenticated multi-host Mesh recovery remain unqualified.

Standalone, Orchestra-bound and Mesh Agents share the same native TCP ingress limits. Read describe_agent.request_ingress or the registration/heartbeat payload for kyuubiki.agent-request-ingress/v1, effective limits, active connection count and reserved raw request bytes. Configured connection/aggregate-byte limits cover the general pool; a small fixed recovery reserve is reported separately and in total limits. Changes require a process restart; invalid configuration rejects startup.

  • KYUUBIKI_AGENT_MAX_REQUEST_BYTES: default 268435456 (256 MiB), accepted 1 through 536870912 (512 MiB). Empty or oversized frame lengths are rejected before allocating or waiting for the body.
  • KYUUBIKI_AGENT_MAX_IN_FLIGHT_REQUEST_BYTES: default 536870912 (512 MiB), accepted 1 through 1073741824 (1 GiB), and at least the per-request limit. Reservation precedes allocation and is retained through dispatch/reply, then released on completion, error or unwinding.
  • KYUUBIKI_AGENT_REQUEST_TIMEOUT_MS: default 30000, accepted 1 through 300000. Idle, header and body reads share one total budget per request; fragments cannot renew it. This is not a solver deadline. A persistent connection gets a new budget after the prior request and its response finish.
  • KYUUBIKI_AGENT_MAX_CONNECTIONS: default 64, accepted 1 through 256 general connections. After both general and recovery slots fill, excess sockets close without spawning handlers or entering an application queue. A handler spawn failure releases its socket/slot without shutting down the listener.
  • request_ingress.recovery_reserve publishes the read-only kyuubiki.agent-recovery-ingress/v1 policy on the same listener: four additional connections, four in-flight reserved requests, at most 16 KiB per reserved frame (or the smaller configured request limit), and at most four times that frame size in reserved encoded bytes. Defaults therefore permit 68 total handlers and 512 MiB + 64 KiB retained input. max_total_connections and max_total_in_flight_request_bytes expose these total bounds; aggregate usage includes both pools, with general/reserve counters also visible.
  • Connection overflow is control-only for that socket's entire lifetime, even after general capacity returns. General byte-budget overflow can use the reserve for that frame only. Reserved reception gets at most 1,000 ms (or the smaller configured timeout) from the original frame-receive start, including idle/header/body. Falling back does not reset that clock. Partial input, decode failures and unwinding return reserved permits.
  • The explicit allowed_methods list covers ping/description, lifecycle inspection/drain/resume, durable inspect/list/cancel, operator result lookup and existing execution/job cancellation. Normal RPC validation, loopback-only lifecycle mutation and identity/store fences still apply. Solver, TaskIR, durable submission and other methods cannot use the reserve: a valid forbidden request receives agent_recovery_ingress_only and the connection closes without task admission. No client-side alternate port, hidden retry, owner transfer or automatic task replay is introduced.

Invalid framing, size overflow, exhausted total capacity and receive timeout close the connection before dispatch. No task receipt or automatic retry is created. A complete invalid JSON frame can return invalid_json without corrupting framing for the next request. Clients must still preserve a durable handle after an uncertain submission: a generic disconnect alone does not prove that admission never happened. The byte budget covers encoded input, not decoded objects, solver memory or whole-process RSS. The recovery reserve can itself be occupied by slow or abusive callers. Reply deadlines remain separate, and there is no sustained-overload availability guarantee or authenticated LAN protection. Configure limits for expected payload size and transfer time, not merely node count.

Single-Agent direct execution and recovery

The native frontend gateway can bypass Orchestra for direct solving. A Workbench direct-mode run with exactly one endpoint now uses the durable contract. This is not a claim that all Workbench workflows run without Orchestra. Existing /api/direct-mesh/solve results still use a process-local cache.

  • Configure KYUUBIKI_AGENT_EXECUTION_STORE to a dedicated, absolute directory in the deployment's writable state. Its parent must already exist. The Agent creates the final directory; Unix permissions must be owner-only. One Agent process holds its exclusive directory lock. No implicit home-directory store or memory fallback is created.
  • The existing owner.lock stores a synced, checksummed random 32-hex-character identity. An empty legacy lock is initialized once; a nonempty invalid identity fails startup rather than being silently replaced. The descriptor, receipts, index, cancellation and live admission rejection expose store_id. This is non-secret routing identity, not authentication; copying a complete ledger copies its identity. Old native clients can omit expected_store_id, but then have no protection against a different ledger taking over the address.
  • The desktop-managed runtime now provisions a separate agent-executions/agent-<port> under its writable state on Agent startup. Override the parent with KYUUBIKI_AGENT_EXECUTION_STORE_ROOT, an absolute directory. Runtime status displays the root and the Agent descriptor displays the concrete directory and limits. Managed startup rejects the standalone single-directory override to prevent multiple Agents sharing one ledger. Already-running Agents need an explicit managed restart to receive this configuration.
  • run_durable_agent_task accepts a caller-generated execution_id (32 lowercase hex characters), a solver RPC method, and object params. Execute-mode run_operator_task_ir also uses this boundary. The Agent writes and syncs the admission before dispatch, and the checksummed final receipt before returning. The engine and operator implementations stay unchanged.
  • The synchronous durable owner retains its execution state through receipt commit, then through network response delivery. Successfully sending an error response is not successful execution: a failed receipt commit records durable_receipt_commit_failed in the live watchdog unless that generation already has an earlier failure (such as cancellation). That earlier cause is preserved. The ledger remains outcome_unknown, not a fabricated terminal failure. Synchronous unwinding releases the owner with a live durable_execution_aborted diagnostic but does not commit a panic receipt. These diagnostics are not restart-safe completion proof.
  • submit_durable_agent_task accepts the same task but returns after reserving an execution slot and syncing admission, without waiting for computation. Its worker has no submitting socket, so losing that connection does not cancel the task. Existing capacity, drain, watchdog and exact cancellation rules still apply. The slot stays owned through receipt commit; no unbounded background queue is introduced.
  • If the Agent cannot reserve an execution slot (for example busy or draining), it commits the task identity and a failed receipt before replying, without queuing or calling the engine. The normal execution schema has status: failed and nested error code durable_admission_rejected, with details.execution_started: false. The same ID stays terminal after restart; duplicate submits return that failure and changed inputs are rejected. The receipt is queryable/indexed even if the submit reply was lost. This records a pre-execution failure, not a numerical solver failure.
  • If admission succeeds but owner setup or worker startup fails before the task is handed to the worker, the Agent commits a failed receipt with durable_execution_start_failed, details.phase: before_engine_dispatch and details.execution_started: false. A bounded ownership handoff keeps the slot and admission in the Agent's submit handler until thread creation succeeds; failed creation cannot drop them before receipt commit. The receipt survives tested process termination and duplicates do not re-execute. Commit failure remains uncertain; a missing receipt after restart is never inferred to mean execution did not start. This does not change any solver implementation.
  • An asynchronous worker that unwinds from a Rust panic discards its response and commits durable_execution_panicked as a failed receipt, while retaining the execution slot through the commit attempt. This means the attempt failed, not that nothing ran: execution_may_have_started: true and external_effects_rolled_back: false are explicit. The fixed receipt message does not copy the panic payload. No result or automatic replay is authorized. Shared locks are never unpoisoned by this handler. This boundary excludes ledger commits, synchronous execution, aborts, memory exhaustion and process termination; missing receipts after those events stay unknown.
  • For both synchronous and asynchronous durable TaskIR execution, fetch_operator_task_result publishes only the response from the committed durable receipt, not the solver's earlier return value. An async panic therefore exposes the same failed response through both recovery paths. A failed commit abandons any still-pending cache entry as result_not_retained, without publishing success. This remains a bounded process-local cache: expiry, eviction, ambiguous attempt identities and restart can make it unavailable. Duplicate durable submissions never rebuild it or re-execute the task. Ordinary non-durable TaskIR execution retains its existing completion-before-delivery behavior.
  • If a returned response violates the RPC response contract, exceeds the receipt byte limit, cannot serialize, or cannot be decoded by the restart reader, the Agent discards that response before writing any receipt payload. It commits a small failed receipt with durable_response_unrecordable and a reason of invalid_response, byte_limit, serialization or restart_decode. Only that successful commit makes the failure authoritative; other tasks can then proceed without restarting the Agent. The cache and watchdog follow the committed failure rather than the discarded solver response. This does not prove that nothing executed or that external effects were rolled back, and duplicates never re-execute. If the small failure receipt itself cannot commit, the execution remains unknown and new durable admissions stay blocked. The size limit is unchanged; this is failure isolation, not large-result storage.
  • A valid checksum is not enough to establish a terminal result. New and retained responses must have the supported RPC version, the original request identity, and exactly one valid success or failure state. Successful durable execution requires a non-null top-level result; nested null fields remain valid. Failure code and message must be nonblank. An invalid existing receipt causes an inspection error, not a replacement failure receipt or permission to replay. The file and caller recovery identity remain intact. The admission index and unrelated valid executions stay usable. The native gateway and frontend also reject blank failure evidence before accepting a terminal receipt.
  • When the ledger itself lacks capacity, an asynchronous submit may return kyuubiki.agent-durable-admission-rejection/v1 with status: not_admitted, execution_started: false, automatic_replay_authorized: false, and reason store_capacity. Clients also recognize the earlier transient execution_unavailable decision. Its execution ID, method, input digest, process identity and live RPC request ID bind the decision to this exchange. This is a successful admission decision exchange, not a successful computation or a persisted execution receipt. The native gateway verifies that binding before forwarding. Existing identities, conflicting inputs, corrupt storage and write failures never become this definitive rejection; an ordinary RPC/HTTP error is not proof of non-admission.
  • fetch_durable_agent_execution queries that exact ID. States are not_found, running, completed, failed, or outcome_unknown. Completed/failed records contain the original nested RPC response. An interrupted admission without a receipt is unknown, not proof of failure before execution. No state grants automatic replay permission.
  • durable_execution.store_access publishes the read-only kyuubiki.agent-store-access/v1 policy. Description never waits for the execution-store mutex: contention returns enabled: true, available: false and unavailable_reason: store_busy, omitting dynamic counters and store identity rather than inventing empty values. Poisoned locks report store_unavailable and are never bypassed. Keep any previously saved owner fence; temporary metadata absence does not authorize an unfenced submission or adoption of a different store.
  • Fetch, list and exact cancellation wait at most a 250-ms monotonic budget to acquire the store mutex. Contention returns RPC error durable_execution_busy, not not_found, an empty index or cancellation success. Details state operation_started: false, execution_state_known: false and identity_check_performed: false. These describe this recovery request, not the original task. Nothing is queued to execute later. Retry recovery explicitly on the original Agent/store only; no automatic retry, task replay, peer reselection or migration is authorized. The native HTTP gateway preserves failure rather than creating a result.
  • The 250-ms budget bounds mutex acquisition, not filesystem work, other locks, scheduling delays or reply delivery. Admissions and receipt commits retain the existing serialized durability boundary. A stuck filesystem can still stall its holder and writers; description remains responsive to this store lock while other recovery calls fail busy. This is not physical power-loss or sustained-contention qualification.
  • Persist the chosen Agent and execution ID on the caller side before submitting. Repeat IDs with identical inputs return the existing state or receipt; changed inputs are rejected. Retry only against the same Agent with the same preserved store. Replacing or deleting that store removes its deduplication history. These IDs are not authentication credentials.
  • list_durable_agent_executions takes limit (1 to 64) and optional after (execution ID). It reads only admission metadata, not result receipts; IDs sort lexicographically, not chronologically. next_cursor is the final ID when another page exists. This is not a snapshot across pages; refresh from the first page to include newly admitted IDs that sort before the cursor. An index row is not evidence of successful or completed computation.
  • A known admission disappearing during the current Agent process is an explicit recovery error, not not_found or permission to reuse its execution ID. The bounded ID set is rebuilt at startup and extended after successful admission; it retains no inputs or results. An orphan receipt also rejects fetch and duplicate submission after restart. Listing checks missing admissions and orphan receipt names before pagination, without reading receipt payloads. Other intact executions remain independently readable and runnable. Stop the Agent before restoring original records, then inspect rather than replay. This guard cannot detect complete deletion of all execution evidence across restart; its visible missing_admission policy makes that limit explicit. See the missing admission report.
  • Immutable records publish through same-filesystem hard links, then remove the pending name and sync the directory where supported. Unlike overwriting rename, publication fails if any destination entry exists. The visible record_publication policy requires hard-link support and forbids unsafe fallbacks. Failed exclusive staging creation does not delete a preexisting .next entry. At startup, pending names are removed before reading records; they are never promoted into completed results. A published final record survives cleanup of its pending alias, while an admission without a final receipt stays unknown. No new format, backup or replay authority is introduced. This does not protect arbitrary concurrent external mutation or certify power loss. See the immutable publication report.
  • cancel_durable_agent_execution requires the inspected execution_id, process_instance_id and request_digest. It can mark only the original live async owner, never a later task reusing a job or transport request ID. Its requested receipt explicitly has execution_terminal_confirmed: false. Query again to observe the persisted final result. This control neither replays work nor creates pending cancellation for a future execution; synchronous wrappers have no async owner and are not cancelled through this convenience control.
  • A lost cancellation reply proves neither acceptance nor termination. Inspect the saved Agent/store/execution identity instead of resending or selecting a peer. After forced restart, a synced cancellation failure remains a failed receipt; an admission without a terminal receipt remains outcome_unknown. No in-memory cancellation intent is treated as a durable terminal outcome.
  • For an explicit local fault fixture only, set KYUUBIKI_AGENT_FAULT_INJECTION_STORE_READ_HOLD_FILE to an absolute path before startup. A regular file of at most 128 bytes containing the exact execution ID holds a fetch after owner validation and store-lock acquisition, for a 10-second hold budget or until removed. It is disabled by default and described under store_read_fault_injection. This simulates lock contention, not an actual stalled device; fault-file I/O is not deadline-controlled.
  • The Rust HTTP gateway exposes POST /api/direct-mesh/tasks with execution_id, study_kind, input, and a single allowlisted endpoints entry. Query via POST /api/direct-mesh/tasks/inspect with the same endpoint and ID. Responses expose execution and endpoint. Submission uses asynchronous admission, while inspection reads the Agent ledger rather than the gateway's in-memory result cache. Unknown transport outcomes preserve this handle and never trigger cross-Agent failover. An HTTP 200 alone does not mean computation succeeded: inspect execution.status and the nested response.
  • Submission replies must match the exact execution_id, solver method and locally computed typed binary64 input digest. This also applies to not_admitted: a well-formed digest for another payload cannot authorize cleanup. A not_found lookup is never a submission acknowledgement. Mismatches return HTTP 502 with the original endpoint/ID and no retry or replay permission. Repeated submissions may return the original process and request IDs when the payload matches; inspection does not compare the stored payload with an edited GUI form. These checks bind reply content, not remote authentication. See the submission identity report.
  • The native gateway also exposes POST /api/direct-mesh/tasks/list and POST /api/direct-mesh/tasks/cancel, carrying the corresponding RPC fields plus one allowlisted endpoints entry. Both enforce the same gateway token and return a validated recovery envelope. Neither route uses Orchestra history or the gateway result cache.
  • On Unix, live store operations also revalidate the private owner.lock file against the held lock's device/inode and checksummed store identity. Moving the directory, replacing the lock (even with the same bytes), or corrupting its identity makes durable storage unavailable rather than missing or silently redirected. The descriptor exposes available: false and unavailable_reason: store_binding_unavailable. Recovery checks and new submissions fail without replay permission; a finishing worker cannot publish a receipt to a detected replacement. Stop the Agent before relocating or restoring storage, then inspect the original execution after restart. A missing terminal receipt remains outcome_unknown. The visible live_store_binding policy distinguishes Unix owner-file validation from the unqualified Windows handle boundary. These checks do not serialize arbitrary concurrent filesystem mutations. See the live store binding report.
  • Native durable-route failures remain HTTP 502, with the diagnostic agent_error_code preserved only from a valid, request-bound RPC failure. Codes are limited to 1..128 ASCII letters, digits, underscore, hyphen or period; transport errors, invalid replies and rejected codes expose null. The original error message remains available. Peer error details are not forwarded, so they cannot override the gateway's automatic_retry: false or automatic_replay_authorized: false. An error code is not an execution receipt, owner echo or proof of non-admission. The discovery transport policy exposes these diagnostic bounds.
  • Workbench distinguishes direct:store_busy, direct:store_unavailable and direct:store_write_failed before reserving or submitting a new task. Temporarily unavailable identity metadata is not an old-Agent upgrade requirement. Saved handles remain intact. The HTTP client exposes bounded codes as WorkbenchRequestError.agentErrorCode. Submit, cancel and legacy solve failures are not generic retryable actions; inspect the original execution instead. Inspect/list may be explicitly retried as reads on that same owner. No client automatically retries an error, clears a handle, substitutes a result or switches peers based on its code.
  • The frontend runtime client exposes submitDurableDirectStudy and inspectDurableDirectExecution. Its recovery helper saves a caller-owned handle before sending, pins gateway and Agent, and only inspects after reconnect. Handle storage failure blocks submission; connection changes fence late responses. The ordinary run button and PWDT job/run use this service for exactly one declared Agent. They check its durable capability before reserving a local identity; disabled/old Agents fail closed, without a synchronous fallback. Multi-Agent selection still uses its existing synchronous route and has not acquired this recovery guarantee.
  • Before dispatch, the Workbench stores only the execution ID, endpoint, persistent Agent store identity, study kind, gateway-address digest and creation time. Desktop uses the native desktop-direct-execution.json journal; normal browsers use kyuubiki-direct-execution IndexedDB with strict durability requested. Desktop host failure never falls back to browser storage. There is no RAM fallback, model copy or token persisted. Limits are 64 pending identities and 64 KiB for the native journal; one pending reservation per gateway/Agent blocks duplicate runs across views. Browser storage remains subject to browser/user eviction.
  • New Workbench submissions require a valid persistent Agent identity before saving the handle and dispatching. Old handles without it remain visible and block replacement runs; inspect, cancel and acknowledgement fail closed. Never attach the currently reachable Agent's identity to an old handle to bypass this check. Restore the original evidence or explicitly retire the development state with its callers stopped.
  • A validated live rejection releases only the newly reserved caller identity, permitting a later explicit run with a fresh ID; it never automatically retries. A connection change after local reservation but before dispatch also releases only that caller's unsent reservation. For a retained busy/drain failure, a lost reply or interrupted local cleanup can be reconciled by explicitly inspecting the original terminal receipt; this does not change the model/result. Lost transient capacity decisions, failed local reservation acknowledgement and incomplete receipt writes remain conservative: no replay and no deletion based on not_found. Transient decisions cannot be reconstructed from absence after restart. Every retained failure consumes one entry within the existing ledger limits, without separate backups or automatic eviction. A failed cleanup is reported as direct:journal_cleanup_pending, not success or permission to bypass the journal.
  • In direct mode, open Workbench System > Runtime > Direct Execution Recovery. The panel is collapsed and performs no reads until requested. It lists 24 admissions per page, inspects one receipt, and asks for confirmation before cancellation. GUI and PWDT share directExecution/pending, directExecution/list, directExecution/inspect, and directExecution/cancel. Pending handles supply their saved owner; manual inspect/cancel requires storeId from the original index. Subsequent pages use the same storeId. A supplied identity may not override an existing pending handle. Inspection returns bounded status/identity metadata to action history, not numerical result arrays. It does not replace the current model or result. Unknown, not-found and transport failures never authorize resubmission. Ordinary synchronous solves do not appear in this ledger. Use Local Pending Executions after a lost response or UI restart. Inspecting a matching terminal receipt clears only that caller reservation, not the Agent receipt. Unknown/not-found records remain pending. Ordinary cancel routes the current direct handle to its original Agent, never an Orchestra job ID; cancellation registration does not clear observation or mark the job cancelled. Automatic observation is bounded to 40 inspection reads. Cancellation uses the shared feedback ownership guard: a late reply or failure cannot overwrite a newer terminal message even for the same execution and polling epoch. The cancellation action still returns its own outcome; this feedback guard does not cancel, retry or change backend execution.
  • Recovery action parameters are copied before awaiting the local journal; reusing a caller's payload cannot redirect inspection or cancellation. In-flight ownership checks include control mode even when no API token is configured, alongside effective gateway URLs and applicable credentials. A changed context cannot publish a late receipt or authorize journal cleanup. Once a check observes changed or unreadable authority, that request stays invalid even after settings are restored. Return to the original context and explicitly inspect its saved handle; there is no automatic resubmit or cancel. Managed settings, gateway and in-memory credential writes also advance per-dimension session revisions. Switching away and back between reply checks therefore cannot revive an old request. These are five fixed-size in-memory identities, not credentials or a persistent history. Theme/language, unchanged normalized values, unused tokens and query-masked gateway edits do not invalidate unrelated requests. Settings cleanup and legacy scrubbing use the same guard; partial writes that throw still record actual changes. A single window-lifetime storage listener also observes other same-origin windows' local-storage settings and gateway changes. It compares event old/new values, so a delivered switch-away-and-back notification retires the old request even if storage already holds the original value. It never imports another window's credentials or replays work. Session storage and unrelated preferences are ignored; malformed/oversized relevant settings, inaccessible storage and clear notifications conservatively revoke old authority. Event parsing is bounded to 65,536 string code units per value. Storage events are asynchronous, not a cross-window transaction lock: replies processed before notification delivery are not covered by this fence. Unmanaged same-window storage writes and untracked URL/history mutations still have only snapshot-based roundtrip detection.
  • API authority captures also belong to one active document lifetime. An observed pagehide retires existing guards even if pageshow arrives before the next guard check; calls captured while suspended cannot become valid after restoration. Fresh explicit calls may inspect the original execution. Ordinary backgrounding, blur and a cancelled navigation do not retire work. One lifecycle listener pair is shared per window, with no persisted epochs or per-request listeners. Direct submission checks this guard around storage and transport: only its own confirmed unsent reservation may be released; an already submitted execution keeps its identity when a late reply is rejected. This covers callers using the authority guard, not every raw HTTP request. Chromium/PWDT tests use controlled page-transition events and mocked Agent responses; they do not qualify actual BFCache restoration or installed WebView.
  • Terminal receipt cleanup retains the original observation/recovery guard through its asynchronous scope and journal reads; it cannot adopt a newer caller context. Browser deletion rechecks before/after database open, after its queued transaction read, and on delete-request success while the transaction can still abort. A rejected guard aborts that transaction and preserves the exact reservation for fresh explicit inspection. An already published valid numerical result is not rolled back by cleanup failure. The desktop bridge checks before and after its initial host handshake and before posting deletion, without serializing the guard or credentials. It rechecks again after the reply await before handing success to the caller. Configuration writes are not atomic with storage commits: a change delivered after the final active browser check, or after native deletion was dispatched, cannot be promised to undo deletion. These are local commit-boundary checks, not a cross-process authorization transaction or physical durability guarantee; uncertain cleanup never authorizes automatic resubmission.
  • Desktop direct-execution and model-checkpoint journal hosts snapshot request metadata and page ownership before queueing. An iframe load retires previously accepted requests even when its WindowProxy identity is unchanged. Host pagehide retires and suspends requests; pageshow accepts fresh requests without reviving the old queue. Detached/replaced frames and disposed hosts also fail the dispatch/reply check. Retired queued operations never reach native storage, and late success or failure cannot reply to the replacement document. The eight-request bound remains occupied until earlier native work drains; reload cannot reset it to admit unbounded work. Fresh explicit inspection can reconcile a reservation already committed by an in-flight native call. Both UI bridges use v2 envelopes: a metadata-free connect handshake performs no native call, and every journal read or mutation must echo the host's current random session identity. Load/pagehide rotates that identity, so an old message first delivered after replacement is rejected before native dispatch. An old handshake can only receive a no-data response; a new client ignores its unmatched request ID. No v1 or missing-session fallback is allowed. Client pagehide rejects pending work, including handshake waiters; pageshow permits fresh explicit operations without automatic replay. One shared handshake and at most eight logical calls bound client state. Expiry rejects the current operation; only a later explicit call reconnects. Pair the updated embedded frontend with the updated desktop shell; native journal files need no migration. Session identities live only in memory, not in URLs, journals or credentials. A reply already received but not yet returned to the caller is checked against lifecycle and caller ownership again. Pagehide, disposal or guard loss in that interval rejects the continuation without sending rollback or replay commands. This is not Agent authentication or navigation-start atomicity: calls dispatched before an observed lifecycle change can still commit. Client timeout alone does not withdraw queued work or roll back native storage. Local Chromium tests use real cross-origin iframe navigation but mocked native invocation, not installed WebView, physical disk or power-loss qualification.
  • The ledger stores at most 1,024 admissions, 8 MiB per encoded receipt, and 128 MiB of retained record bytes, with capacity reserved for active receipts. It keeps no model-input copies or backup generations. Capacity exhaustion rejects new work instead of silently evicting identities. Clear a disposable ledger only with the Agent stopped and callers retired.

Qualification includes real local Agent process kills before computation, after durable receipt sync but before reply delivery, and after completion, with repeat restart and duplicate-submission checks. This is not physical power-loss qualification or a claim of mid-solver numerical continuation. Installed-WebView-to-real-Agent qualification, multi-Agent durable selection, full workflow-graph execution and TLS/authentication parity remain separate work. The direct transport still requires a trusted network boundary; do not expose the raw Agent listener publicly. See the scoped test report. The asynchronous admission report records the detached-worker, shutdown and frontend recovery-interface checks. The recovery controls report tracks the separate Agent index, exact-owner cancellation and GUI/PWDT checks. The default-run report adds native caller process-kill, browser reload and ordinary run/cancel coverage. The Mesh recovery report also covers lost cancellation replies, truncated cancellation requests, local forced restarts, same-execution feedback races and late receipt isolation after token-free control-mode changes and roundtrips in a separate browser fixture.

Operational goal

Each deployment mode should remain legible in terms of storage, discovery, authority, and update behavior. Documentation should make those tradeoffs visible instead of hiding them in environment files.

Local background-service lifecycle

Hub, Workbench, Installer, and the native runtime command share one Rust lifecycle implementation. The GUI is a control client, not the lifetime owner of computations: closing a window or quitting the GUI does not stop background services. Start, stop, and restart remain explicit actions. There is no implicit OS-login startup or automatic crash-restart policy.

  • Start: validate the requested ports and existing ownership, then start local agents, Orchestra, and the optional frontend gateway. A repeated start reuses only verified, listening service instances.
  • Start failure: detect an early process exit without waiting for the full readiness timeout; terminate a child whose registration or readiness fails, and roll back only services created by this operation. Existing services are preserved and cleanup failures are reported.
  • Stop: stop the frontend gateway, Orchestra, and local agents in reverse startup order. A failure on one service does not skip cleanup of the other owned services or produce a false success.
  • Restart: hold the same OS-backed lifecycle lock across stop and start. A competing mutation fails as busy; status remains readable. A controller crash releases the lock without deleting its lock file.
  • Recovery: a later controller can inspect and stop registered background processes left by an interrupted launcher. Dead PID records are reconciled. Unverified live processes and inconsistent records fail closed.

Readiness here means a live, ownership-verified process and a listening local port, not proof of API health, solver correctness, or completion of in-flight research. Stop is an explicit service shutdown, not a job-draining contract; checkpoint or complete important tasks before stopping the stack.

Visible state, scope, and ownership

Installed payloads remain separate from writable state. Use KYUUBIKI_RUNTIME_ROOT for the installed payload and KYUUBIKI_RUNTIME_STATE_ROOT for its external writable state. Status reports the resolved runtime paths, lifecycle policy, lock location, and service readiness. Source mode uses the repository's tmp/run.

  • <runtime-state>/run/lifecycle.lock is a persistent, small OS-lock file, not a stale-lock marker to delete manually.
  • Each managed service has a PID file and a *.process.json ownership record with schema kyuubiki.runtime-process/v1, process incarnation, label, port, and canonical state-directory identity. It stores no launch environment, credentials, or command-line secrets.
  • PID reuse, a copied record from another state directory, or a live legacy PID without an ownership record never authorizes automatic adoption or termination. An occupied unmanaged port is blocked, not a healthy running service.
  • KYUUBIKI_ORCHESTRATOR_PORT and KYUUBIKI_FRONTEND_PORT select validated nonzero ports; defaults are 4000 and 3000. Nondefault ports have distinct PID and log filenames. Local agent ports come from the configured discovery source.
  • KYUUBIKI_RUNTIME_ORCHESTRATOR_ONLY limits mutations to Orchestra; KYUUBIKI_RUNTIME_FRONTEND_DISABLED excludes the frontend gateway. Distributed mode does not start or stop local agents. Use consistent scope settings across start, status, and stop.

During an upgrade from legacy PID-only management, stop old services with their existing controller before switching controllers. Do not fabricate ownership records or delete live PID files to force adoption. An interrupted registration with inconsistent files requires diagnosis, not blind cleanup. OS service registration, task draining, and supervised restart with backoff are separate follow-up work, not guarantees of this lifecycle layer.

Lifecycle regression tests

The native tests use temporary payload/state directories, dynamic ports, and a Rust listener, without Node, shell launch scripts, database services, or the workstation's default service ports. The same scenarios run on macOS and Linux; Windows-specific paths also receive compilation checks. These fixtures validate process management, not the full production stack. 

cargo test --locked --manifest-path workers/rust/Cargo.toml -p kyuubiki-platform -p kyuubiki-desktop-runtime

Remote deployment maturity

Installer remote deployment is currently a policy-bounded SSH pilot, not yet a full production deployment service. The roadmap is to move toward explicit deployment plans, durable journals, artifact delivery, host trust, and physical/containerized remote tests. The first structured plan preview now lives in the Installer CLI as remote-deployment-plan, with matching journal preview records available through remote-deployment-journal and artifact delivery preview through remote-artifacts.
