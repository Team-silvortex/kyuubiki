注册与账号入口：2026-11-13

  1. 打开 Workbench → 商店 → 账号。填写管理员提供的 HTTPS 账号站点地址，可包含端口， 不能包含凭证、路径、查询参数或片段。此配置与目录源独立，默认不猜测生产或局域网站点。
  2. 保存后核对目标地址，点击“注册 / 账号网站”。入口固定为该站点的 /account?lang=zh 或 /account?lang=en， 不臆造后端尚未提供的注册专用路由。日语等其他界面语言暂使用账号网站的英文页。
  3. 在 Team Silvortex 账号网站选择注册，按网站要求完成邮箱验证及认证。 Kyuubiki 不接管密码、验证码或双重认证；本机只保存公开站点地址，不保存账号凭证。
  4. 完成注册后返回原工作区，在“连接工作台账号”的折叠设置里填写已登记的公共桌面客户端 ID、 固定回调端口，保存后点击“连接账号”。密码和验证码始终只在系统浏览器的账号站点输入。
  5. 只有原生层验证回调、令牌签名和当前用户身份成功，才显示“已连接”。 浏览器已有登录 cookie、打开网页或返回应用均不算登录成功。注册不授予 Agent 控制权限。

桌面壳通过专用 Rust 命令请求系统浏览器打开页面，不调用 Node 或 shell。 消息桥只接受固定本机前端窗口和来源，拒绝未知字段及不安全地址，并处理重复请求、失败和超时。 普通浏览器使用带 noopener noreferrer 的新标签页；工作区保持打开。 旧安装包若没有此命令，会提示复制公开目标地址或更新桌面应用，不静默成功。

自部署目录和本地计算不强制注册中心账号。账号网站可移除，存储失败明确提示； 窄屏仍需展示注册步骤、错误和会话边界，不能被通用精简样式隐藏。

会话与安全边界

客户端读取 issuer 的 discovery，并核对账号、token、userinfo、JWKS 和 revoke 都属于该 issuer 的现有固定路径。强制 HTTPS，不跟随重定向、不继承环境代理；私有 CA 必须同时提供 公开 PEM 和其 DER 内容的 SHA-256 指纹，并通过可信渠道独立核对。浏览器的站点信任需要另行配置。

本机监听只绑定 127.0.0.1；回调限定 GET、Host、路径、大小、总等待时间、 单值 state/iss/code，拒绝重放和混合错误响应。ID Token 必须通过 RS256 签名、issuer、audience、 nonce、时间和 subject 检查，并与 userinfo 对应。登录与刷新只允许一个事务在途，退出及取消令旧事务失效。

令牌只保存在原生进程内存，不发给 WebView，不进入 localStorage、项目或配置文件。 页面只保存公开站点、client ID、回调端口及公开 CA 设置，接收脱敏会话状态。进程退出后需重新登录。 “续期会话”使用轮换刷新令牌；响应丢失或验证失败就清除本地会话，不自动重试旧刷新令牌。

“退出工作台账号”先清除本地身份，再尽力撤销令牌；网络失败会显示 revocation_unconfirmed，不能声称远端已撤销。此动作不会清除网站 SSO cookie。 当前没有全局浏览器退出、持久登录、纯浏览器登录回调或跨应用即时注销通知；原生页内状态查询不等同于服务器实时验证。

协议参考：RFC 8252 原生应用授权、 OpenID Connect Core。 身份实现独立于求解引擎和算子，登录不改变本地研究、Agent 控制或包验签的权限边界。

登录后的授权下载：2026-11-13

实现以 Silvortex 后端仓库的 contracts/kyuubiki/store-v1.openapi.json v1.2.0 和 docs/apps/kyuubiki-store-publishing.md 为准。 当前仅接受与已登录 issuer 同源的 /store/v1，不把账号令牌交给任意目录源、URL 或 CDN。

  1. Workbench → 商店 → 账号完成连接，再进入“授权下载”。“账号商店目录”直接查询已登录 issuer， 支持搜索和每页 20 条的游标分页；选中条目带入资源 ID、返回的确切版本和本机平台，仍需用户确认预检。 也保留手动输入确切版本的入口。目录换代或游标失效需回到第一页，不混合不同目录快照。 本轮不从旧目录引用的 package_ref 推断托管身份，不提供含糊的 latest 下载。
  2. 填写独立可信渠道取得的签名 key_id 及公钥 SPKI DER 的 SHA-256。 这是发布传输签名公钥，不是 TLS CA 指纹、OIDC 登录公钥或私钥；客户端不自动信任服务器返回的新根。
  3. “预检版本和额度”查询 capabilities、me、entitlements、固定版本详情和 trust-roots， 核对账号、平台、发布状态、文件边界和签名。此步骤不创建授权、不扣额度。 预检后折叠输入区，将待确认记录放到主要位置；支持中、英、日和窄屏布局。
  4. 核对记录后显式点击“授权并下载”。算子和工作流模板始终提示可能消耗一次额度， 即使预检时不限额度也不承诺后续权益不变。授权前先落盘不可变文件清单和幂等键， 按后端 grant_issued 策略核对返回的原始计次结果。
  5. 短期票据只用于同源的固定下载路由；下载请求不带账号 Authorization，不跟随重定向。 校验 RS256 对小写 SHA-256 ASCII 文本的传输签名、准确长度及流式摘要后， 才将暂存目录切换为已校验文件。不会自动加载算子、运行脚本或显示“已安装”。

恢复、磁盘与安全边界

  • 原生服务独立于 React、求解引擎与算子；UI 只提交受限操作，接收脱敏状态。 消息先进行不含业务参数的页面握手，再绑定页面代次提交操作；刷新后旧页面请求不得重放。 access/refresh token 和下载票据均不写入本地记录、项目、浏览器存储或日志。
  • 记录保存在桌面偏好目录下的 store-downloads/<operation-id>/record.json， 本次临时文件为 partial/，完成文件为 files/。 Unix 目录 0700、文件 0600；拒绝符号链接、路径穿越、Windows 保留名称和大小写/文件目录冲突。 文件、目录与记录写入设有同步点；实际断电/强杀注入仍未验收。
  • 最多 4 条记录，单文件 64 MiB、单次 32 个文件且总量 256 MiB；串行写入并使用跨进程锁。 只清理本操作的失败暂存；不清扫用户项目。用户可确认移除已完成记录，未确认的授权结果禁止直接遗忘。
  • 授权响应丢失时沿用原请求体和原幂等键，即使剩余额度已经为零也允许恢复查询。 已知授权重试只续签原 grant，不新建授权；取消不退额度。本轮按整文件重试，尚无 Range 断点续传。
  • 列表额度是预检或原授权时的快照，不冒充实时余额。另一应用实例可能仍在下载， 无本进程执行句柄的记录显示“未完成，需核对或恢复”；跨进程锁阻止重复运行或并发移除。
  • 授权重放期限不超过后端声明的幂等保留期，并预留时间余量；超过期限停止自动 POST， 不能假定旧键永远不会重复扣次。票据过期、召回、撤销或会话失效均由服务端再次判定。
  • 退出/续期使旧下载租约失效，迟到的旧 401 不得清除新会话。完成提交与当前会话串行核对。 网络请求有时限，取消不能瞬间打断在途阻塞读取，单文件请求最多等待 120 秒。
  • 重开面板可恢复原生下载状态；本机进程退出后会话不保留。重新登录后的旧 grant 续签是否允许， 取决于服务端的原会话约束，不能承诺跨进程自动恢复。当前测试覆盖管理器重建与记录复读， 不将它计作真实进程崩溃或跨会话续签通过。

  3. 每个平台最多暂存 8 个包；动态库不超过 32 MiB，清单不超过 64 KiB。 单一受锁的 pending 目录、文件同步与原子目录提交避免半包成为可见包；重试清理自己未完成的 pending，不累积历史备份。 相同包幂等确认，同名不同版本或不同摘要拒绝覆盖。下载缓存删除不删除部署缓存。 缓存自动淘汰、在线版本替换及专用清理界面尚未实现，不静默删除已启用的包。
  4. 项目请求新增可选 platform：缺省或 null 使用本机安装库；显式 Linux 值使用隔离的暂存库和项目记录， 即使控制端本身是 Linux 也保持此规则。项目启用、准备与分块读取不依赖商店登录，退出账号后仍能工作。
  5. 目标核验、上传、清理上传、执行前核验都固定所选平台。目标返回“ready”也不能跳过平台检查。 平台切换清掉旧包、旧任务预览和旧就绪显示；控制通道或进程身份变化仍阻止后续请求。 原有 TLS、API token、直接控制准入与版本冲突保护不变。
  6. variant_staged 仅证明本机暂存，installed_restart_required 仅证明目标安装。 Linux Agent 的实际动态加载、宿主版本和运行库依赖须在目标机确认，核验磁盘包与已加载包一致后才能进入 ready。

加载失败诊断与显式恢复：2026-11-13

新增的 activation_failed 是宿主级故障，不是上传未完成，也不说明只有当前包有问题。 回执必须满足 installed 与请求固定身份一致、active 为空、字节计数完整；activation_error 仅允许 operator_package_activation_failed、operator_package_integrity_failed、 operator_package_count_mismatch。其他状态不能附带非空故障码，故障和 ready 不能同时成立。 详细库路径、加载器错误和符号诊断只写 Agent 本机日志，不放入包部署回执。

原生算子进程隔离：2026-11-13

Agent 不再在控制进程加载外部动态库。启动探测及每次执行都使用同一个原生 Agent 二进制的内部子进程入口， 不引入 Node、shell 或额外安装组件。引擎保留底层动态 ABI 加载能力，Agent 负责进程监督；商店、包部署和任务控制仍彼此解耦。

  • 一次调用一个宿主进程：构造器、算子入口、ABI 解码 / 释放、库卸载都在子进程内。调用结束后终止并回收， 不保留插件全局状态，不自动重试失败任务。下一个显式任务使用新进程，启动开销是当前故障隔离的取舍。
  • 启动阶段固定包身份；每次执行重新加载、复核清单与入口摘要和算子列表，身份变化时不调用入口。 active 表示该 Agent 启动验证通过的固定身份，不再表示动态库常驻于 Agent 地址空间。 既有 generation lease 持有到子进程完成清理，避免缓存轮换提前删除正在执行的包。
  • 默认加载预算 10 秒、执行预算 300 秒，均为包含通信和库加载 / 卸载的整次调用时间。 可通过 KYUUBIKI_OPERATOR_PROCESS_LOAD_TIMEOUT_MS 与 KYUUBIKI_OPERATOR_PROCESS_RUN_TIMEOUT_MS 配置为 100..3600000 毫秒，0 或无效值拒绝启动；运行时描述和执行回执公开生效策略。
  • IPC 仅绑定回环临时端口，使用随机 32 字节握手，凭据通过继承管道传入而不是命令行或环境变量。 帧上限 64 MiB，部分读写不续期；不继承 Agent、商店或模型令牌环境，仅保留系统与临时目录变量。 插件 stdout / stderr 当前丢弃，不作为通信通道，也不生成无界日志。
  • 执行崩溃返回 operator_process_crashed，超时返回 operator_process_timeout， 通信违规返回 operator_process_protocol_failed；取消仍沿用 cancelled，阶段为 execute_external_process。失败回执要求检查后显式重跑，不以自动重试掩盖重复副作用。
  • Unix 宿主在读取请求和加载动态库前必须确认自己是独立进程组的组长，拒绝共享进程组入口。 正常清理终止自有进程组并回收宿主；父 Agent 被强制终止时，仍存活的宿主看门狗通过管道 EOF 终止最初确认的自有进程组，包括未脱离该组的辅助进程。回执的 parent_loss_cleanup 在 Unix 为 owned_process_group，Windows 为 direct_child_only。 Unix 子进程关闭 core dump，避免故障产生大型磁盘转储。启动探测失败仍沿用既有策略：显式部署模式保留诊断入口，默认严格启动不静默放行。

  • Agent 返回 operator_package_dispatch_failed，不发布成功结果；失败回执保留原任务和算子身份， 不自动重试。真实故障用例确认宿主退出，之后显式提交的健康任务仍可执行。

2. 分工与不可混淆的边界

  • 中心商店后端：对接 Team Silvortex 身份，提供商品目录、不可变版本元数据、 服务端权益判定、下载授权、作者资格、上传审核和下载计量。订阅、付款方式验证及分成规则留在该部署的私有策略中。
  • Kyuubiki：Workbench 项目工作流、通用源适配器、原生安全下载与安装、 验签及兼容性检查、项目版本锁定、安装状态查询和 SDK/PWDT 对等调用。
  • 开源自部署：可使用机构或本地目录，不强制注册 Team Silvortex 账号， 不依赖托管订阅。机构可配置自己的访问策略；“无需中心账号”不意味着任意远程端点均可访问。
  • 运行时：商店权限不授予 Agent 控制权。执行引擎不导入 GUI，也不实现支付逻辑。 Orchestra 模式下，算子库由绑定的 Orchestra 管理，Agent 按需取得任务依赖，不保存全部商店副本。
  • 直连和 Mesh：通过受管的本地包缓存及已有运行时准入策略交付依赖，不隐式创建 Orchestra。 项目引用、下载缓存、已准入包和正在执行的任务是四种不同状态。
  • 产品政策：中心商店免费用户有有限下载额度，订阅用户可获得不限次数权益； 具体数值、周期、计费事件和作者分成比例由后端返回，客户端不硬编码。额度不足不能阻止本地计算。

4. P0 后端需求：目录、身份、下载

以下为建议的托管适配器路径，前缀 /store/v1 待双方确认。 不要求把这些私有策略放入 Kyuubiki 仓库。提供 OpenAPI 与固定测试数据后，Kyuubiki 接入同一通用源接口。

发现与目录

  • GET /store/v1/capabilities：返回 API 版本、资源种类、身份模式、 分页上限及下载/发布是否启用。不支持的能力必须显式禁用，不能用空成功响应冒充实现。
  • GET /store/v1/assets?kind=&q=&domain=&cursor=&limit=&locale=： 建议默认 24、上限 100 条，稳定排序和不透明游标；返回下一页游标与目录修订号。 目录更新使游标失效时返回可恢复的 catalog_changed，不得重复或跳过条目。
  • GET /store/v1/assets/:kind/:id/releases/:version：返回不可变发布元数据、 作者标识、许可证、简介、领域/标签、依赖、更新说明、支持平台、运行时/Worker SDK/TaskIR 兼容范围、 各目标摘要与字节数、签名和来源证据引用。
  • 源身份由本地可信配置决定，远端不能自行冒充 builtin.local。 资源唯一选择为 source + kind + id + version + target + digest，不使用标题或 email 作为主键。
  • 明确 active、yanked、recalled 的含义； 撤回和安全召回不得改写已有版本内容。缺少目标或兼容信息应阻止安装，而非乐观猜测。
  • 搜索需返回完整资源引用而非执行代码。文案当作文本，详情富文本需要消毒； 外链和图标只允许明确的安全协议，不能触发本地文件、shell 或任意网络代理访问。

共享身份与权益

  • 复用 Team Silvortex 的 OIDC Authorization Code + PKCE S256，或双方明确的受管会话网关。 需提供测试 issuer、公开客户端标识、允许的桌面/浏览器回调、audience、scopes、登出与撤销语义。
  • 以 issuer + subject 标识用户，校验 state、nonce、issuer、audience 和过期时间。 UI 不接收 client secret，不保存密码；访问/刷新令牌不得写入项目文件、localStorage 或日志。
  • 持久凭证未来须接入经过验收的原生安全存储；纯浏览器优先安全 HttpOnly 会话并保护 CSRF， 无持久安全通道时仅在内存保留短期材料。不要新增明文配置目录存 token 的捷径。
  • GET /store/v1/me：最小显示信息及会话到期状态。 GET /store/v1/me/entitlements：可下载种类、限额、剩余额度、重置时间、 是否无限以及发布资格。不限次数也保留合理限流，不能把“无限”解释成无安全限制。
  • 发布资格需服务端确认账号状态和有效付款方式；只返回资格/阻断原因， 不返回卡号或付款凭据。免费额度与订阅规则留在中心服务，客户端不得自行判定放行。

授权下载与重试

  • POST /store/v1/download-grants：提交固定资源版本、目标和摘要， 带 Idempotency-Key。授权绑定当前主体与不可变制品，并返回 grant id、 短时 HTTPS 下载票据、有效期、摘要、长度和本次额度处理结果。
  • 同一主体、幂等键、相同请求必须返回同一逻辑授权；相同键配不同内容返回冲突。 额度预留/扣减与授权写入必须同一事务。成功响应丢失后重试不能再次收费或扣额。
  • POST /store/v1/download-grants/:id/renew：续签失效票据， 不重复计次；重校验授权主体、撤销及安全召回。提供 GET /store/v1/download-grants/:id 查询中断后的结果。幂等记录保留周期和额度事件规则需在契约中明确。
  • “授权已签发”不等于下载完成。P0 建议按唯一授权计额度，统计中分开授权数、 完整制品下载数和安装回执；作者收益的有效下载及反作弊规则另行确认，不信任客户端自报。
  • CDN 支持 Range、ETag、准确 Content-Length 与重试。下载票据不是账号 token； 不得将身份 Authorization 头转发到第三方 CDN 或跨源重定向。票据也必须从日志中脱敏。
  • 客户端只访问配置允许的 HTTPS 来源，重新检查重定向；自部署 HTTP 只能显式启用受信来源。 服务器不能因目录带一个 URL 就成为任意地址下载代理。

6. P1 Kyuubiki 原生安装闭环

此阶段由 Kyuubiki 跟进，不能只凭后端的下载成功响应改 UI 为“已安装”。 工作区引用清单保持轻量；安装回执由实际运行时或受管包库提供。

  2. 通过共享原生下载服务处理授权、断点续传和取消，使用有配额的临时缓存， 同一制品内容寻址去重；没有新的 shell/Node 安装脚本。
  3. 检查字节数、摘要、签名信任根、撤回状态、平台与协议兼容性及依赖。 限制解包大小/文件数量，拒绝路径穿越、软链接逃逸和覆盖已有包。

Rust API 为 kyuubiki_installer::prepare_operator_distribution； CLI 与其共用实现，不新增 Node 或 shell 打包脚本。先在对应工具链上编译，再显式提供各目标动态库。 以下输出目录的父目录必须已存在，输出目录本身必须不存在。

cargo run --locked --manifest-path workers/rust/Cargo.toml -p kyuubiki-installer -- \
  prepare-operator-distribution path/to/kyuubiki-operator.json candidate \
  aarch64-apple-darwin=build/apple-arm64/libexample.dylib \
  x86_64-unknown-linux-gnu=build/linux-x64/libexample.so

这是命令形状示例；请替换为实际构建产物，不会自动下载或生成这些文件。 输入包清单的身份、算子列表、SDK/ABI、最低宿主版本和验证状态被保留，只把入口路径重定位为 包内 operator.dylib / operator.so / operator.dll。 许可证等中心商品元数据走提交外壳，不往严格执行清单里塞未知字段。

  • aarch64-apple-darwin → macos-aarch64。
  • x86_64-apple-darwin → macos-x86_64。
  • aarch64-unknown-linux-gnu → linux-aarch64。
  • x86_64-unknown-linux-gnu → linux-x86_64。
  • x86_64-pc-windows-msvc → windows-x86_64。

当前明确不接受 universal、musl、GNU Windows 或未列出的目标，避免把 不同 ABI 静默塞进同一平台键。每份 manifest 上限 1 MiB、每份库上限 512 MiB，最多五个目标； 以流式复制计算摘要，只检查复制后的文件头，不加载待发布代码。拒绝空文件、符号链接、重复目标、 错误架构和未知清单字段；包身份共用安装器的可移植校验，提前拒绝 CON/NUL 等保留名。 索引按平台排序，输入顺序不会改变输出；已有目录不覆盖。

输出为 candidate/kyuubiki-operator-distribution.json 与各平台子目录。 上传后放到既有 <package-id>/<version>/ 布局，不把构建缓存、源码、测试数据库 或本机路径打包进去。失败会清理本次暂存；并发使用输出锁，正常异常路径释放。 强杀可能留下锁或隐藏暂存，确认原打包进程已退出后才能清理。本入口不是断电恢复服务。

文件头检查仅验证格式、字长、CPU 与相应共享库类型标记，不能证明导出符号、 依赖库、glibc/系统最低版本、代码签名或算法正确。实现依据 Apple Mach-O 定义、 ELF 头规范和 Microsoft PE 规范。 构建声明的 Rust ABI 仍需构建证据核实，不能仅凭文件头证明 GNU/MSVC 来源。

CI 与验收边界

.github/workflows/operator-store-release-candidate.yml 为手动触发的模板包验收流程。采用各平台原生 runner 构建，显式指定 Rust target； 当前不是在一台 Mac 上交叉链接所有系统。每个任务先跑打包拒绝测试，编译 release 库， 再通过 Installer 安装、Agent 实际执行与卸载，全部成功才生成五目标汇总索引。 Runner 标签依据 GitHub 官方说明， 不使用已退役的 macOS 14 标签。候选制品保留七天，无中心商店凭证，不自动公开发布。

这一流程只为仓库内的模板包产生可复现证据；第三方包需要对应的测试输入、 预期输出及兼容基线。不能把模板成功当作所有算子通过，也不能把文件头模拟测试当作远端平台执行。

发布后端原始交接要求与当前边界

以下为原始交接要求，不再表示全部未实现。 2026-11-11 已完成隔离后端与真实 macOS 包联调，见下方验收；正式入口及客户端投稿仍需接通。

  1. 按目标接收完整制品集：复用 operator-package-distribution/v1，每个目标分别上传 manifest 和 entrypoint， 保留其独立 SHA-256 与长度。服务端重新计算，不用单个 ZIP 摘要替代内部摘要； 若接收 ZIP，须限制展开体积、文件数和路径并拒绝链接。不能信任客户端声明的成功状态。
  2. 事务式 finalize：先验证声明目标全部到齐、清单身份一致、文件摘要一致、 路径安全，再封存不可变版本。相同幂等键重试不得创建第二份版本；同一版本不同内容必须冲突。 一个平台上传失败时不能公开半个声明矩阵；允许发布单目标版本，但必须显式声明，不能自动降级。
  3. 构建与兼容元数据：在商品发布外壳中提供 Rust target、源码修订、锁文件摘要、 工具链、构建模式、runner/CI 关联号，以及最低 OS、libc/CRT 和依赖库约束。 v1 平台键不足以区分 GNU/musl/MSVC，当前候选器先拒绝不支持的变体；扩展前需共同版本化契约。 本地文件路径不作为远端构建证据。
  4. 签名和审核独立：发布服务不运行上传的库。隔离审核环境完成目标平台加载与 算子测试，验证状态和证据须绑定具体目标与摘要；再产生可校验签名、key id、撤回/召回状态。 不把作者写入 manifest 的 validation_status 当作服务端审核结论。
  5. 最小联调交付：提供 submissions / uploads / finalize / status 的 OpenAPI 和测试环境，以及一个 macOS arm64 小包。覆盖少目标、错误 CPU、摘要不符、重复 finalize、 响应丢失后重试、拒绝审核和撤回。返回稳定错误码、请求关联号，不返回服务器目录或令牌。
