Tutorial 04 · Rust Headless SDK

Run a material screen without the frontend

This tutorial uses the repository CLI as a thin example over the Rust Headless SDK. It proves inspect -> validate -> plan -> mock -> service execution while keeping every durable artifact outside the source tree.

Template: heat spreader screening Three candidates Mock first, service second Reports retained
Tutorial center Headless SDK reference Material research example
Step 1

Discover, do not guess

./scripts/kyuubiki headless templates --category materials --json
./scripts/kyuubiki headless suggest "thermal material screening" --json

Select the exact template id material_heat_spreader_screening. Template titles are for people; ids are the automation contract.

Step 2

Initialize and inspect the batch

./scripts/kyuubiki headless init \
  --template material_heat_spreader_screening \
  --workflow-id tutorial.material-heat-spreader \
  --out tmp/tutorial-material-heat-spreader.json \
  --json

./scripts/kyuubiki headless inspect \
  tmp/tutorial-material-heat-spreader.json \
  --json

Checkpoint: the summary reports nine service steps: three solve, wait, and result-fetch groups for three named candidates.

Step 3

Validate and retain the plan

./scripts/kyuubiki headless validate \
  tmp/tutorial-material-heat-spreader.json \
  --json

./scripts/kyuubiki headless plan \
  tmp/tutorial-material-heat-spreader.json \
  --out tmp/tutorial-material-heat-spreader.plan.json \
  --json
  • Validation must report ok: true and zero unresolved issues.
  • The plan must identify a service-only runtime and an explicitly compatible executor.
  • Review confirmation requirements before adding --execute.
Step 4

Prove orchestration with mock execution

./scripts/kyuubiki headless run \
  tmp/tutorial-material-heat-spreader.json \
  --execute --executor mock \
  --material-report material_heat_spreader_screening \
  --material-report-out tmp/tutorial-material-report.mock.json \
  --report-out tmp/tutorial-run-report.mock.json \
  --json

A mock run proves validation, ordering, bindings, reporting, and failure plumbing. It does not produce solver evidence and must never be presented as material research.

Step 5

Execute against a live service

./scripts/kyuubiki headless run \
  tmp/tutorial-material-heat-spreader.json \
  --execute --executor service \
  --execution-posture research \
  --api-base-url http://127.0.0.1:4000 \
  --job-wait-timeout-ms 1200000 \
  --material-report material_heat_spreader_screening \
  --material-report-out tmp/tutorial-material-report.service.json \
  --report-out tmp/tutorial-run-report.service.json \
  --json
  • Use the configured control-plane address for your environment; the loopback value is only the local example.
  • Keep API credentials in the caller-owned secure credential path, not in workflow JSON, source files, or shell history.
  • Research posture accepts the service executor and rejects mock-capable research claims.
  • A timeout override changes this client wait budget, not server execution policy or the source workflow.

Completion contract

A delivered request is not an executed task. For native operator_task_execute batches, blocked or pending runtime receipts stop the chain and do not count as completed computation. Explicit blocked execution returns a nonzero exit code, with headless_execution_blocked on JSON stderr; the requested run report is still written. Inspect the blocking step's execution_readiness.required_action, repair that gate, and retry explicitly. Mock TaskIR execution is only a blocked preview.

Orchestra also validates Agent task identity and completion at its own API boundary. Batch reports distinguish attempted, executed, blocked, failed, and skipped cases. A zero error count alone cannot authorize checkpoint archival: complete task-bound result coverage is required. Use resolve_incomplete_cases for mixed failure/blocking/skipping, inspect retained recovery actions, and explicitly execute only the approved recovery targets. Local API regression is not installed or scientific qualification.

An agent_native task is dispatched as TaskIR to the Agent, not converted back to a legacy solve RPC. Unbundled tasks declaring the boolean agent_fetchable: false do not require an external-package runtime; tasks with package references and central fetch tasks still do. The native headless-live-test includes a real local Agent/Orchestra chain for axial-bar execution, input repair, downstream side-effect blocking, and checkpoint reload. This is local development evidence, not installed-app acceptance.

A delivered failed execution receipt may use HTTP 200 while its status is failed. Inspect the task-bound failure_receipt.reason_code, failure_stage, and recovery.required_action; do not branch on HTTP success or message text. Native Rust reports retain this Agent receipt and derive their typed recovery summary from it. Repair explicitly: retry advice never permits automatic task replay or failover. A validated unsafe-continuation flag stops independent batches and retains skipped targets.

The real local HTTP tests also cover 2D/3D modal TaskIR, full mode shapes before report compaction, independent reference roots/residuals, and recovery after invalid density. These small unit-beam fixtures do not qualify arbitrary geometry, remote scale, or installed deployment.

TaskIR cancellation retains task identity and a typed failure stage. Inspect inspect_cancellation_before_explicit_rerun before explicitly rerunning; cancellation never authorizes automatic retry or downstream actions. A previously recorded watchdog timeout remains the terminal cause. The final publication gate runs after heartbeat shutdown and checks both cancellation and the current watchdog generation. An observed shutdown-time failure is retained as a failed original-attempt receipt, not the computed success value. Legacy solver RPCs also recheck after serialization. There is no atomic cancel-versus-send guarantee after the last gate. Native solver checkpoints are diagnostic, not resumable snapshots. Local HTTP regressions directly cancel an owned Agent before computation and during 2D/3D modal calculation, then verify side-effect isolation and same-task rerun. A separate two-real-Agent regression covers the public asynchronous job cancel route and isolates incorrect-peer routing. Deterministic publication-boundary tests have separate Rust unit coverage; they are not real-heartbeat transport fault qualification. Remote and authenticated deployment remain unqualified.

For POST /api/v1/jobs/{job_id}/cancel, inspect the separate cancellation acknowledgement. requested means registration was acknowledged, not that the native computation has stopped. partially_requested, delivery_failed, and no_active_dispatch must not be treated as global execution shutdown. Known dispatch endpoints are retained until caller cleanup; queued requests are cancelled locally. Native cancellation and package-cache cleanup have separate results, and execution_terminal_confirmed remains false.

The native watchdog's 16-entry recent-failure list is diagnostic only. A failed execution's original reason and identity remain shared by its live execution guards even after list eviction, so late solver or transport callbacks do not overwrite the cause or count the failure twice. This per-execution record is released with the last guard and does not survive Agent restart. A known failure can still be returned when watchdog state becomes unavailable; new execution admission remains closed. Legacy solver decoding and result-encoding failures also keep the original reason in both the outer RPC error and its details. Without a prior failure, they retain invalid_params and result_transport_failed, respectively. An explicit rerun uses a new generation.

For one observed execution, the separate native cancel_execution RPC requires the exact process_instance_id, request_id, positive integer generation and job_id from describe_agent. The control request has its own RPC id. Missing, null, unknown or malformed fields fail with invalid_params; identities are bounded to 256 UTF-8 bytes and are not normalized. Unavailable process identity fails with agent_lifecycle_unavailable without cancellation. Its kyuubiki.agent-execution-cancellation/v1 acknowledgement echoes the target. requested means the matching live control was marked, not confirmed termination; target_not_observed is not proof that the original computation never ran. Neither creates pending job cancellation, cleans package caches or authorizes replay. This fence is not authentication. Local real-Agent tests cover sibling/peer isolation, stale generation and restart identity reuse. See the native request example and limits.

The Rust SDK now exposes cancel_operator_task_dispatch(task_id, task_digest, attempt_id, &target). Explicitly choose an attempt from inspect_operator_task_dispatch and decode its active observation's execution_target as CancelExecutionRequest; null or absence is not a target. The write-authorized POST /api/v1/operator-tasks/cancel-dispatch sends exactly that target through the retained original endpoint/session fingerprint, without retargeting, job-wide fallback, journal mutation or publication. Inspect its kyuubiki.operator-task-dispatch-cancellation/v1 status: transport failure or invalid acknowledgement means cancellation_outcome_unknown and cancel_registered: null, not confirmed rejection. SDK errors do not grant automatic retry. The control round trip is bounded to five seconds and 64 KiB; the SDK shares a ten-second HTTP deadline. Three real local TaskIR cancellation chains now use this public SDK path, retain typed failure and downstream isolation, and explicitly rerun. The legacy job-cancel route remains unchanged. This observed target is not initial-process attestation, durable cancellation intent, Python/Elixir parity or deployed qualification. See the public SDK example and recovery rules.

The direct Agent cancel_job RPC keeps one-shot pre-admission cancellation: if no matching execution control is live, cancellation applies to the next admission with that job id. Do not send a late job-wide cancel merely to clean up an already-terminal attempt; it can affect a same-job explicit rerun. Inspect the original attempt's receipt separately. Precise cancellation must use cancel_execution, not this job-wide fallback.

Native synchronous operator_task_execute steps now send a separate execution_budget envelope. Defaults are 120 seconds of queue waiting, 120 seconds of Agent RPC waiting and 10 seconds of connection/framing allowance, under one HTTP deadline. Configure OperatorTaskRequestBudget::new(queue_ms, execution_ms) with with_operator_task_budget, or override a step's envelope. Both phases are bounded to 1..600000 ms. Task digest and numerical settings are unchanged; metadata requests and asynchronous job polling keep their own policies. Budgeted TaskIR is not replayed after send/receive failure.

After a disconnected TaskIR request, use executor.inspect_operator_task_dispatch(task_id, task_digest) to inspect retained dispatch observations in a fresh connection. Orchestra checks only the original currently configured Agent fingerprint; it neither broadcasts nor reruns. Active requests are diagnostic, and absence remains unknown. The bounded journal retains no model, result or credentials, fails closed on corruption or saturation, and keeps ownership across the locally tested Orchestra process restart. This is not a final-result cache, a remote cancellation route, an exactly-once guarantee, or deployed qualification.

Choose an original attempt explicitly, then call executor.fetch_operator_task_result(&task, attempt_id). This separate read fetches and verifies a computation receipt from that Agent without reexecution, publication or journal mutation. Retention is memory-only: 64 entries, 8 MiB per encoded response, 32 MiB total encoded responses, and 10 minutes from reservation creation. Metadata and transient JSON allocations are additional. Expiry, eviction, oversize, ambiguity and Agent restart leave the outcome unknown; none grants replay. A recovered failed or blocked receipt is not execution success, and computation completion is not durable delivery acknowledgement.

Transport timeout means operator_task_outcome_unknown, not confirmed cancellation. The native report marks it nonretryable and stops downstream actions; inspect the task and owning Agent before explicitly rerunning. A silent HTTP calculation can outlast the old 30-second idle cutoff, but response framing remains bounded at 64 MiB. These are per-step waiting limits, not whole-batch or solver CPU termination guarantees. Remote/installed qualification remains separate.

For local backend regression, run mix test in apps/web. Default SQLite tests now own a unique temporary database and clean it after stopping the application; they do not reuse the development database. An explicit SQLITE_DATABASE_PATH remains caller-owned and must point to disposable test data. Local HTTP/Agent tests need loopback socket permission, but do not require an installed background service.

Move from CLI example to Rust embedding

Use the official Rust package and examples once the command path is understood. The CLI is an example adapter, not the upper limit of Headless integration.

Official Rust execute_model_headless_plan checks single-task and batch completion before advancing. A blocked, partial, stale, or contradictory task receipt produces a v2 failed plan receipt with the original step output and authority retained. Use operator_task_recovery_summary to find readiness repair actions, repair the gate, and execute an approved plan explicitly. Low-level ControlPlaneClient methods return raw HTTP receipts; their Ok alone does not certify computation. This Rust gate is not a claim of Python/Elixir parity or numerical qualification.
