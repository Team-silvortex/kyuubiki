Tutorial 04 · Rust Headless SDK

Run a material screen without the frontend

This tutorial uses the repository CLI as a thin example over the Rust Headless SDK. It proves inspect -> validate -> plan -> mock -> service execution while keeping every durable artifact outside the source tree.

Template: heat spreader screening Three candidates Mock first, service second Reports retained
Tutorial center Headless SDK reference Material research example
Step 1

Discover, do not guess

./scripts/kyuubiki headless templates --category materials --json
./scripts/kyuubiki headless suggest "thermal material screening" --json

Select the exact template id material_heat_spreader_screening. Template titles are for people; ids are the automation contract.

Step 2

Initialize and inspect the batch

./scripts/kyuubiki headless init \
  --template material_heat_spreader_screening \
  --workflow-id tutorial.material-heat-spreader \
  --out tmp/tutorial-material-heat-spreader.json \
  --json

./scripts/kyuubiki headless inspect \
  tmp/tutorial-material-heat-spreader.json \
  --json

Checkpoint: the summary reports nine service steps: three solve, wait, and result-fetch groups for three named candidates.

Step 3

Validate and retain the plan

./scripts/kyuubiki headless validate \
  tmp/tutorial-material-heat-spreader.json \
  --json

./scripts/kyuubiki headless plan \
  tmp/tutorial-material-heat-spreader.json \
  --out tmp/tutorial-material-heat-spreader.plan.json \
  --json
  • Validation must report ok: true and zero unresolved issues.
  • The plan must identify a service-only runtime and an explicitly compatible executor.
  • Review confirmation requirements before adding --execute.
Step 4

Prove orchestration with mock execution

./scripts/kyuubiki headless run \
  tmp/tutorial-material-heat-spreader.json \
  --execute --executor mock \
  --material-report material_heat_spreader_screening \
  --material-report-out tmp/tutorial-material-report.mock.json \
  --report-out tmp/tutorial-run-report.mock.json \
  --json

A mock run proves validation, ordering, bindings, reporting, and failure plumbing. It does not produce solver evidence and must never be presented as material research.

Step 5

Execute against a live service

./scripts/kyuubiki headless run \
  tmp/tutorial-material-heat-spreader.json \
  --execute --executor service \
  --execution-posture research \
  --api-base-url http://127.0.0.1:4000 \
  --job-wait-timeout-ms 1200000 \
  --material-report material_heat_spreader_screening \
  --material-report-out tmp/tutorial-material-report.service.json \
  --report-out tmp/tutorial-run-report.service.json \
  --json
  • Use the configured control-plane address for your environment; the loopback value is only the local example.
  • Keep API credentials in the caller-owned secure credential path, not in workflow JSON, source files, or shell history.
  • Research posture accepts the service executor and rejects mock-capable research claims.
  • A timeout override changes this client wait budget, not server execution policy or the source workflow.

Completion contract

Native research run reports capture execution_input before dispatch or payload compaction. Evidence requires that versioned fingerprint to match the effective batch, not merely its workflow ID and validation summary. Changed physical inputs need a new explicit run; correcting only a metric mapping may reuse the unchanged batch and captured report. Old reports remain readable but cannot be backfilled with new input identity. The batch fingerprint is not authenticated execution or external-model content binding. See the input identity contract and limits.

Saved-reference solves also capture model_source and accept an optional expected_model_source pin. Changed saved content refuses before submission; research evidence requires matching source identities and pins. This records the fetched snapshot, not normalized solver bytes or an Agent attestation. See saved model sources and recovery.

Large native FEM uploads verify prepared and transmitted bytes before solver submission, retaining model_artifact_upload. Axial-bar Pa/GPa normalization and ten-route field graph ID/object rules match inline and file transport, including steady advection-diffusion. Native result_fetch extracts actual physical JSON through bounded verified readback, default 64 MiB; resolve_result_artifact: false retains references without downloading. Native saved-version solves can use Orchestra scheduling without explicit Agent endpoints. Readback failures stop later steps without computation replay. Remaining solver normalization and parsed-result capacity stay open. See the remaining transport boundaries.

For a retained material research bundle, import the original file through MaterialResearchBundle::from_json_verified(&text) in either Rust SDK. This checks structure and four embedded artifact digests without re-encoding key order, number tokens or string escapes. Formatting whitespace is allowed. In-memory validators and Python/Elixir helpers check structure only; digest agreement is not authenticated provenance, whole-bundle metadata protection or numerical qualification, and later object edits require explicit re-verification. See the research bundle import regression.

Native library writes validate explicit project/model/version identities, parent associations and repeated fields before publishing bindings. Malformed 2xx replies stop as service_request_outcome_unknown with a library_receipt_invalid detail and no replay, even if the database write already happened. Project deletion requires the existing HTTP 200 project receipt, not an empty 204. Registered native FEM version solves preserve the saved version reference in the server-side job; this is association validation, not full model or scientific validation. See the library and saved-version regression.

Saved model/version reads validate the requested record and parent identities before submitting computation. Do not combine a saved reference with inline input or model_payload. Invalid reads stop with model_reference_invalid under contract_failure at validation, without a compute request, bindings or automatic retry. Native mesh fallback preserves verified project/version context; a mutable model is not labeled as its latest saved version. Existing study/material overrides remain separate from this identity check. See the saved reference regression and limits.

Native job reads reject padded or conflicting identifiers and malformed result preferences before I/O. Optional project, saved-version and simulation-case hints constrain every returned job; explicit null version means a declared unversioned job. Combined saved-version solve/wait carries the selected version through waiting and result reading. Read association failures stop as job_read_invalid under contract_failure, without later steps or replay. A previous solve may already have happened: reconcile and continue reading, not resubmit automatically. See the read association regression.

Known failed/cancelled job receipts carry explicit terminal markers. Reason text mentioning connection failures, queues, timeouts or authorization cannot turn them into retryable transport errors, during submission or job_wait. Inspect and reconcile before explicitly creating replacement work.

Native asynchronous submissions require an explicit job, a usable unmodified job_id, a public status and consistent repeated fields. A malformed 2xx receipt stops with service_request_outcome_unknown, without bindings, polling, later writes or automatic replay. The server may already have calculated the job. Explicit failed or cancelled jobs remain known terminal failures. Active or completed submission acknowledgements do not certify a numerical result; result fetching keeps its separate gate. See the submission receipt regression and scope.

FEM, composite and explicit mesh submissions also check the project/version fields actually transmitted. Wrong or missing requested association makes the acknowledgement uncertain, even if it claims failure; never replay it automatically. Orchestra rejects contradictory explicit project/version pairs with HTTP 422 and :model_version_project_mismatch before creating work, rather than silently selecting the version's project. Version-only and matching pairs still work. These checks establish consistency, not authorization or scientific provenance. Native workflow SDK context options are not forwarded by this change. See the submission association regression.

A native service write can take effect even when its reply is lost. Once writing has been attempted, missing or invalid acknowledgements and HTTP 5xx replies stop with kyuubiki.headless.service_request_outcome_unknown, retryable: false and no replay strategy. Zero successful steps does not prove zero server-side effects. Inspect the relevant records and reconcile before authorizing an explicit continuation; do not resend the step or entire batch automatically. Deadline requests and streamed uploads share this gate. Complete 4xx replies retain their diagnostics; an empty 204 is a no-content acknowledgement, not a durability guarantee. TaskIR retains its specialized unknown-outcome inspection rules. See the real write-acknowledgement regression and limits.

A delivered request is not an executed task. For native operator_task_execute batches, blocked or pending runtime receipts stop the chain and do not count as completed computation. Explicit blocked execution returns a nonzero exit code, with headless_execution_blocked on JSON stderr; the requested run report is still written. Inspect the blocking step's execution_readiness.required_action, repair that gate, and retry explicitly. Mock TaskIR execution is only a blocked preview.

Native whole-value bindings must exist in the actual completed source result, not just in the action's declared outputs. Missing outputs or null/blank required values stop before the dependent request with kyuubiki.headless.binding_resolution. Completed source work remains completed: repair and explicitly run only the intended downstream actions, rather than replaying the entire batch. Dry-run also stops at missing preview outputs or the first confirmation gate. Full results are bound before report compaction; previews are not resumable checkpoints. See the real-chain binding regression.

The native batch binding cache keeps only outputs referenced by later steps and releases each field on its last use, moving that final value instead of cloning it. Earlier fanout uses remain independent, and full results still reach downstream actions before report compaction. Dry-run/local preparation copy only referenced preview fields. This is not result persistence, automatic replay or a total RSS cap; public result normalization and live branches still allocate. A real SDK/CLI chain stores complete 513-node, 512-element results in new model versions without repeating its source calculation. See the binding lifetime regression and limits.

Native job/result normalization and combined saved-version solve/wait now move original JSON envelopes into their existing output shapes, avoiding extra deep copies. Required public raw/result mirrors remain independent; receipt, association and completed-result gates are unchanged. Real SDK/CLI experiments save full results and add no calculation beyond each explicit solve. This is not an RSS or throughput benchmark. See the result ownership regression and limits.

Native inline JSON uses one bounded encoded buffer and borrowed header/body vector writes, then releases the body before receiving the reply. Oversize rejection still happens before connection with exact byte diagnostics; partial writes keep the original deadline and uncertain writes never authorize replay. Complete multilingual research notes are checked through real SDK/CLI persistence chains. This is not a total RSS or CPU bound. See the request policy and the request buffer regression.

Native reports take ownership of eligible resolved payload and unused result fields rather than copying them. Later bindings still retain complete originals; their independent report previews keep the same thresholds. Array samples do not retain a large source buffer, and overreserved short arrays/strings release excess capacity. Real SDK/CLI checks compare summary samples and Unicode prefixes with full stored data. This is not an aggregate RSS or scale claim. See the report policy and the report compaction regression.

The native Headless example CLI streams JSON through a 64 KiB buffer and publishes each file from same-directory staging. A save failure exits nonzero with report_output_failure while retaining the actual run receipt on writable JSON stdout. Inspect the same job/result rather than rerunning the workflow. Single-file replacement is not a multi-file or power-loss guarantee. SDK consumers choose their own storage. See the publication policy and the recovery regression.

Use distinct files for the workflow, parameter patch, round specification, previous evidence and each requested output. The native CLI rejects aliases and output-file ancestors before execution with output_path_conflict; initial JSON run rejection produces a zero-step stdout receipt and writes no files. Publication rechecks do not make an untrusted directory safe or authorize replay. See artifact path protection and the real-service regression.

A successful run is not proof that material reports or research evidence were generated. Consume the exit status and stderr diagnostic: report_generation_failure retains the actual run but does not authorize replay. Repair mapping only against retained results, then explicitly rebuild and verify derived evidence through the SDK. Combined solve/wait wraps a fetched result one level deeper than plain result fetch. Existing artifact files can be stale; verify hashes and lineage. See post-run recovery and the generation regression.

Before SDK research execution, call validate_headless_research_round_plan on the effective patched batch, spec, receipt and previous evidence. The native research CLI does this before service requests: invalid metric steps, baseline patches or disconnected lineage produce an invalid zero-step receipt, not timeout/replay advice. Valid preflight cannot predict runtime result fields or prove previous evidence authenticity. See the policy and the real-service regression.

For a built-in material report, call validate_material_report_compatibility before executing its effective batch. The native CLI checks complete candidate solves, waits and ordered readbacks before service requests; generic custom workflows remain independent. A swapped or repeated result cannot be treated as a different fixed candidate. Retained-result builders still need complete, correctly associated inputs, and mock previews do not qualify material physics. See the policy and the regression.

Use build_material_report_from_run for a saved typed run, or build_material_report_from_input for JSON with an optional optimization profile. Both fixed-report paths verify complete executed steps, matching fetched job identities and owned candidate solve/wait/read chains. The standalone material report command shares this policy. Failed runs cannot supply partial results, and malformed run records cannot fall back to a raw results array. Regeneration performs no computation; raw arrays remain caller-owned, and explicit mock runs remain previews. See the retained input contract and the five-study regression.

Fixed material reports also require the original candidate's physical input profile. Changing material constants, thickness, boundaries or coupled models requires a custom study/report or a supported materialized-candidate path; synchronizing duplicate SI fields does not make original ranking constants applicable. Generic solve/patch execution and nonphysical annotations remain available. See the input policy and the profile regression.

Native batch risk labels must match the registered action contracts. Imported mismatches invalidate the entire batch before any execution, even when all confirmation flags are supplied. Plans display contract-owned confirmation requirements; sensitive and destructive authorizations remain independent. Regenerate malformed metadata rather than weakening its risk label. See the real-chain risk-gate regression.

Native job_wait verifies the requested job identity and public status. result_fetch requires a matching completed job and an explicit object result, including when prefer_job_result: false. Retained runtime objects from queued, active, failed or cancelled jobs are not completed results. Invalid receipts and unavailable results halt downstream work without automatic retry or resubmission; inspect the same job before an explicit continuation. This availability gate is not scientific or artifact-integrity validation, and separate status/result reads are not an atomic snapshot. See the job-result regression.

Native job_fetch now checks the same exact request aliases and optional project/version/case hints, plus matching reply identity and public status. Invalid replies stop without bindings or later actions. Unlike waiting or result admission, observation of a valid failed/cancelled job succeeds so its reason can be inspected. A successful query or CLI exit does not certify computation; retained diagnostic values are not admitted scientific results. Use result_fetch for the completed-result gate. See the single job observation regression.

Native ordinary reads and upload acknowledgements now have header/wire limits and a nonrenewable total network budget. A read exceeding its budget fails with service_response_limit_exceeded, without retry permission or bindings. An oversized write acknowledgement remains service_request_outcome_unknown: inspect committed records instead of replaying. Large model/results retain a separate 512 MiB wire channel; non-chunked decoding avoids one full string copy, but parsed values and retained result mirrors are not a total memory cap. See the fixed transport policies and the real-chain regression.

Orchestra also validates Agent task identity and completion at its own API boundary. Batch reports distinguish attempted, executed, blocked, failed, and skipped cases. A zero error count alone cannot authorize checkpoint archival: complete task-bound result coverage is required. Use resolve_incomplete_cases for mixed failure/blocking/skipping, inspect retained recovery actions, and explicitly execute only the approved recovery targets. Local API regression is not installed or scientific qualification.

An agent_native task is dispatched as TaskIR to the Agent, not converted back to a legacy solve RPC. Unbundled tasks declaring the boolean agent_fetchable: false do not require an external-package runtime; tasks with package references and central fetch tasks still do. The native headless-live-test includes a real local Agent/Orchestra chain for axial-bar execution, input repair, downstream side-effect blocking, and checkpoint reload. This is local development evidence, not installed-app acceptance.

A delivered failed execution receipt may use HTTP 200 while its status is failed. Inspect the task-bound failure_receipt.reason_code, failure_stage, and recovery.required_action; do not branch on HTTP success or message text. Native Rust reports retain this Agent receipt and derive their typed recovery summary from it. Repair explicitly: retry advice never permits automatic task replay or failover. A validated unsafe-continuation flag stops independent batches and retains skipped targets.

The real local HTTP tests also cover 2D/3D modal TaskIR, full mode shapes before report compaction, independent reference roots/residuals, and recovery after invalid density. These small unit-beam fixtures do not qualify arbitrary geometry, remote scale, or installed deployment.

TaskIR cancellation retains task identity and a typed failure stage. Inspect inspect_cancellation_before_explicit_rerun before explicitly rerunning; cancellation never authorizes automatic retry or downstream actions. A previously recorded watchdog timeout remains the terminal cause. The final publication gate runs after heartbeat shutdown and checks both cancellation and the current watchdog generation. An observed shutdown-time failure is retained as a failed original-attempt receipt, not the computed success value. Legacy solver RPCs also recheck after serialization. There is no atomic cancel-versus-send guarantee after the last gate. Native solver checkpoints are diagnostic, not resumable snapshots. Local HTTP regressions directly cancel an owned Agent before computation and during 2D/3D modal calculation, then verify side-effect isolation and same-task rerun. A separate two-real-Agent regression covers the public asynchronous job cancel route and isolates incorrect-peer routing. Deterministic publication-boundary tests have separate Rust unit coverage; they are not real-heartbeat transport fault qualification. Remote and authenticated deployment remain unqualified.

For POST /api/v1/jobs/{job_id}/cancel, inspect the separate cancellation acknowledgement. requested means registration was acknowledged, not that the native computation has stopped. partially_requested, delivery_failed, and no_active_dispatch must not be treated as global execution shutdown. Known dispatch endpoints are retained until caller cleanup; queued requests are cancelled locally. Native cancellation and package-cache cleanup have separate results, and execution_terminal_confirmed remains false.

The native watchdog's 16-entry recent-failure list is diagnostic only. A failed execution's original reason and identity remain shared by its live execution guards even after list eviction, so late solver or transport callbacks do not overwrite the cause or count the failure twice. This per-execution record is released with the last guard and does not survive Agent restart. A known failure can still be returned when watchdog state becomes unavailable; new execution admission remains closed. Legacy solver decoding and result-encoding failures also keep the original reason in both the outer RPC error and its details. Without a prior failure, they retain invalid_params and result_transport_failed, respectively. An explicit rerun uses a new generation.

For one observed execution, the separate native cancel_execution RPC requires the exact process_instance_id, request_id, positive integer generation and job_id from describe_agent. The control request has its own RPC id. Missing, null, unknown or malformed fields fail with invalid_params; identities are bounded to 256 UTF-8 bytes and are not normalized. Unavailable process identity fails with agent_lifecycle_unavailable without cancellation. Its kyuubiki.agent-execution-cancellation/v1 acknowledgement echoes the target. requested means the matching live control was marked, not confirmed termination; target_not_observed is not proof that the original computation never ran. Neither creates pending job cancellation, cleans package caches or authorizes replay. This fence is not authentication. Local real-Agent tests cover sibling/peer isolation, stale generation and restart identity reuse. See the native request example and limits.

The Rust SDK now exposes cancel_operator_task_dispatch(task_id, task_digest, attempt_id, &target). Explicitly choose an attempt from inspect_operator_task_dispatch and decode its active observation's execution_target as CancelExecutionRequest; null or absence is not a target. The write-authorized POST /api/v1/operator-tasks/cancel-dispatch sends exactly that target through the retained original endpoint/session fingerprint, without retargeting, job-wide fallback, journal mutation or publication. Inspect its kyuubiki.operator-task-dispatch-cancellation/v1 status: transport failure or invalid acknowledgement means cancellation_outcome_unknown and cancel_registered: null, not confirmed rejection. SDK errors do not grant automatic retry. The control round trip is bounded to five seconds and 64 KiB; the SDK shares a ten-second HTTP deadline. Three real local TaskIR cancellation chains now use this public SDK path, retain typed failure and downstream isolation, and explicitly rerun. The legacy job-cancel route remains unchanged. This observed target is not initial-process attestation, durable cancellation intent, Python/Elixir parity or deployed qualification. See the public SDK example and recovery rules.

If either the native or HTTP cancellation acknowledgement is lost, preserve the selected attempt and observed target; do not resend cancellation or run the task again automatically. Fetch the original receipt with fetch_operator_task_result(&task, selected_attempt_id), and match task/digest/attempt plus request/process/generation to the saved identities. A typed cancelled failure and a successfully executed original receipt are different outcomes even when cancellation looked unknown. Missing or inconsistent receipt stays unknown. Reading does not publish downstream results or rewrite the dispatch journal, which can still say outcome_unknown. The bounded Agent-memory cache does not survive Agent restart and is not a durable delivery acknowledgement. Any rerun needs explicit authorization after inspection.

Three real acknowledgement-loss chains have been verified on macOS and in a remote Linux source-test container. A test-only relay consumes the actual native or HTTP reply before disconnecting the caller, including a negative cancellation reply after computation has completed. The tests retain exact identity, original-receipt recovery, no automatic replay or peer fallback, downstream isolation and an explicit healthy rerun. This does not qualify installed or authenticated deployments, Agent restart recovery or durable acknowledgement. See the regression report and limits.

Unknown result replies must still be complete v1 envelopes: the SDK requires explicit completion: null, rejects extra fields and validates any supplied execution identity. Orchestra rejects incomplete native envelopes and mismatched fixed retention policy. Real source tests fill the 64-entry cache, lose the original endpoint and restart its Agent; original attempts stay unknown without peer fallback, journal changes or automatic execution. A fresh explicitly authorized attempt cannot replace an old receipt. This is safe handling of lost availability, not durable restart recovery. See the boundary report.

The direct Agent cancel_job RPC keeps one-shot pre-admission cancellation: if no matching execution control is live, cancellation applies to the next admission with that job id. Do not send a late job-wide cancel merely to clean up an already-terminal attempt; it can affect a same-job explicit rerun. Inspect the original attempt's receipt separately. Precise cancellation must use cancel_execution, not this job-wide fallback.

Native synchronous operator_task_execute steps now send a separate execution_budget envelope. Defaults are 120 seconds of queue waiting, 120 seconds of Agent RPC waiting and 10 seconds of connection/framing allowance, under one HTTP deadline. Configure OperatorTaskRequestBudget::new(queue_ms, execution_ms) with with_operator_task_budget, or override a step's envelope. Both phases are bounded to 1..600000 ms. Task digest and numerical settings are unchanged; metadata requests and asynchronous job polling keep their own policies. Budgeted TaskIR is not replayed after send/receive failure.

After a disconnected TaskIR request, use executor.inspect_operator_task_dispatch(task_id, task_digest) to inspect retained dispatch observations in a fresh connection. Orchestra checks only the original currently configured Agent fingerprint; it neither broadcasts nor reruns. Active requests are diagnostic, and absence remains unknown. The bounded journal retains no model, result or credentials, fails closed on corruption or saturation, and keeps ownership across the locally tested Orchestra process restart. This is not a final-result cache, a remote cancellation route, an exactly-once guarantee, or deployed qualification.

Choose an original attempt explicitly, then call executor.fetch_operator_task_result(&task, attempt_id). This separate read fetches and verifies a computation receipt from that Agent without reexecution, publication or journal mutation. Retention is memory-only: 64 entries, 8 MiB per encoded response, 32 MiB total encoded responses, and 10 minutes from reservation creation. Metadata and transient JSON allocations are additional. Expiry, eviction, oversize, ambiguity and Agent restart leave the outcome unknown; none grants replay. A recovered failed or blocked receipt is not execution success, and computation completion is not durable delivery acknowledgement.

Transport timeout means operator_task_outcome_unknown, not confirmed cancellation. The native report marks it nonretryable and stops downstream actions; inspect the task and owning Agent before explicitly rerunning. A silent HTTP calculation can outlast the old 30-second idle cutoff, but response framing remains bounded at 64 MiB. These are per-step waiting limits, not whole-batch or solver CPU termination guarantees. Remote/installed qualification remains separate.

For local backend regression, run mix test in apps/web. Default SQLite tests now own a unique temporary database and clean it after stopping the application; they do not reuse the development database. An explicit SQLITE_DATABASE_PATH remains caller-owned and must point to disposable test data. Local HTTP/Agent tests need loopback socket permission, but do not require an installed background service.

Move from CLI example to Rust embedding

Use the official Rust package and examples once the command path is understood. The CLI is an example adapter, not the upper limit of Headless integration.

Official Rust execute_model_headless_plan checks single-task and batch completion before advancing. A blocked, partial, stale, or contradictory task receipt produces a v2 failed plan receipt with the original step output and authority retained. Use operator_task_recovery_summary to find readiness repair actions, repair the gate, and execute an approved plan explicitly. Low-level ControlPlaneClient methods return raw HTTP receipts; their Ok alone does not certify computation. This Rust gate is not a claim of Python/Elixir parity or numerical qualification.
