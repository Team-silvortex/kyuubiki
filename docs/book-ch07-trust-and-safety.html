Accuracy, trust, and release safety

Solver trust is a first-class product concern. So are safety, installation integrity, update visibility, and release repeatability. The product should be understandable and auditable, not magical.

Back to book Previous chapter Next chapter

Trust pillars

  • Accuracy baselines and expansion plans are explicit.
  • Security and destructive actions stay visible and auditable.
  • Installation and update behavior are configuration-visible and residue-conscious.
  • Credentials live in Kyuubiki-owned sandbox roots, not hidden system-global folders or ordinary project config.
  • Mobile credential access is handle-based through native secure storage; WebView code must not receive raw private keys or long-lived token bytes.
  • Component integrity is a protocol: new components must declare ownership, required paths, protected paths, cleanup scope, and visible rules.

Release expectation

A stronger product line is one where operators can inspect behavior, engineers can verify behavior, and release owners can repeat behavior.

Incremental desktop builds

  • Hub, Workbench, and Installer remain separate applications. They reuse the platform-scoped Cargo cache without merging their UI, identities, or installation paths.
  • Child builds do not inherit the runner's Cargo package metadata. Switching between cargo run and a directly launched runner does not change that build context. Toolchain, linker, and explicit compilation settings are preserved.
  • Shared TypeScript is checked on every build preparation. Resource mirrors are written only when their content differs; unchanged language packs and styles keep their timestamps. Stale generated mirror files are removed without recreating the whole tree.
  • Full-set packaging moves artifacts into a same-filesystem staging area, preserving executable permissions and framework symlinks. A failed build restores the prior bundle set. An interrupted staging area is retained for inspection, not silently deleted.
  • Local macOS iteration can use make desktop-build-host BUNDLES=app to skip DMG creation. Linux supports BUNDLES=deb and Windows BUNDLES=nsis on their native hosts. Release verification and signing requirements remain unchanged.

Build output reports actual resource writes and per-shell elapsed times. Unit tests cover content repair, stale-file cleanup, package rollback, collisions, and filesystem metadata preservation. Native installed-package qualification remains a separate requirement.
