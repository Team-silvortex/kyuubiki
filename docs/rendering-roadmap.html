Rendering Roadmap

daji 3.x render capability upgrade path

This page turns the current rendering reality into a concrete staged plan. The goal is not to chase visual polish first. The goal is to let advanced multi-operator simulation features stay truthful, scalable, and eventually viewport-native.

assessment

Current rendering posture

The current workbench renderer is already good enough for operator growth, workflow debugging, and moderate result inspection. It is not yet a true simulation viewport engine. Most visible rendering still runs through SVG-driven view components and progressive DOM budgeting rather than a dedicated field renderer.

  • strong today: workflow editing, scalar-field selection, result summaries, moderate 2D and truss inspection
  • acceptable with caution: larger studies that rely on progressive batch reveal instead of full interactive density
  • not ready yet: dense plane-field clouds, layered electrostatic plus thermal plus thermo overlays, smooth deform-plus-field playback, Blender-class viewport feel
evidence

Why this assessment is concrete

  • viewport dispatch: apps/frontend/src/components/workbench/workbench-viewport.tsx selects SVG renderers for axial, line, and plane views, and a WebGL geometry layer with SVG picking for 3D trusses
  • render strategy: 2D/plane progressive reveal still uses animation-frame batches. The 3D line-mesh path instead queries a bounded spatial LOD index and reuses GPU buffers when visible membership is unchanged
  • field surface: result fields are already broad in workbench-viewport-core.ts, which means the data model is moving faster than the viewport substrate
  • result chunking: the bounded cache and chunk routes in workers/rust/crates/desktop-runtime/src/direct_mesh_gateway.rs keep large-result access outside the UI thread
rule

Decision rule for the next minors

Keep shipping operator and workflow capability now, but do not pretend the current SVG viewport is the final answer for high-density simulation visuals. New advanced physics features may land before the final render substrate does, as long as they remain inspectable, testable, and performance-bounded.

2026-09-13 / daji 3.2.0 development

Large-model zoom and view-dependent detail

The shared truss_3d, thermal_truss_3d and spring_3d WebGL viewport no longer reveals a file prefix and eventually uploads every node/member. An immutable spatial hierarchy bounds camera queries, clips out-of-view cells and refines visible cells when zooming. Geometry and SVG picking share the same limited set of original objects. Model data, connectivity and solver inputs are not simplified or replaced by the display samples.

  • Auto / Progressive: at most 1,200 node markers and 2,400 members. The 3D Progressive option no longer means eventual full residency.
  • Full: higher-detail LOD, capped at 2,400 nodes and 4,800 members; the control explicitly carries an LOD suffix. It is not an uncapped all-node mode.
  • Focus: at most 600 nodes and 1,200 members.
  • Navigation: wheel zoom anchors the cursor, from 0.08x to 1,024x; F / PWDT viewport/focus3d frames the selection, and R / viewport/reset3d resets zoom and pan as well as orientation.
  • Selection: the active node, selected member endpoints and link draft have priority within the cap. A large multi-selection never bypasses that cap. Box selection targets rendered nodes inside the viewport; use PWDT query/batch selection when the intention is all model nodes.
  • Numerics: global bounds and deformation gain do not change with LOD. Perspective depth follows model scale. GPU positions are rebased to the model center before Float32 conversion. Result-window IDs are resolved explicitly, never confused with array offsets.

Bounded browser acceptance: PASS. The PWDT-driven 100,000-node / 99,999-member regression used actual browser WebGL with an isolated mock backend. Overview retained 1,200 / 2,400 objects; focus on nodes 91,910-91,915 refined to 24 / 31 objects at 162x. Idle frames did not expand or upload the full mesh. Cursor zoom, true-ID picking, reset and resize passed with no WebGL errors. Saving afterwards retained all 100,000 nodes and 99,999 members. Separate regression retains context-loss recovery and fullscreen controls.

Limits: LOD is a visual approximation, not a certified full-field inspection or an assertion that sampled stress extrema equal global extrema. The full input and spatial index still reside in CPU memory; this is not out-of-core model loading. Index construction and model-wide derived state are not background-worker streamed yet. Result paging only exposes loaded data, and cannot invent missing endpoints. Dense plane/solid fields, million-node interactive frame rate, installed WKWebView performance and other native platforms still need separate qualification. This source-level change does not by itself update an already installed App.

Fullscreen modeling workspace

The existing 3D fullscreen surface now contains the real batch, node, quick-property, study and save tools. Inactive batch editors unmount while a lightweight in-memory draft preserves input parameters. No second model snapshot or hidden batch editor is kept for fullscreen.

Undo/redo and query-based actual node selection share existing controllers. The dock resizes by pointer or keyboard within a canvas-first budget; compact layouts retain reachable batch actions. Save and Save As use the project storage service with a busy lock surviving tab remounts. Native fullscreen rejection propagates through PWDT. Browser regression covers five viewport sizes, geometry edits, selection, history and mocked save failures; installed native WebView behavior and solver accuracy are separate qualifications.

See the fullscreen editing tutorial and boundaries. Aspect-fit geometry is retained rather than stretching the WebGL surface away from SVG picking.

2026-09-12 / daji 3.2.0 development

Measured modeling hot paths

CPU measurements below use the real frontend source on macOS ARM64, Node v24.6.0, two warmups and seven timed samples (median), compared against the pre-change implementation at c00e1cb5. These are geometry-edit and scene-preparation measurements, not solver speedups, browser frame-rate guarantees, or a 200k-node interactive GUI qualification.

  • batch property edit, 20k nodes / 10k selected: 31.020 ms to 0.951 ms
  • batch nudge, 20k nodes / 10k selected: 30.169 ms to 0.760 ms
  • batch load assignment, 20k nodes / 10k selected: 31.130 ms to 0.701 ms
  • nearest unconnected node, 10k nodes / 9,999 members: 93.185 ms to 0.321 ms
  • 3D scene buffer preparation, 20k nodes: 35.939 ms to 5.774 ms (without browser CSS parsing or GPU upload)
  • 200k-node bounds and deformation scale: four former argument-stack overflows now complete; planar bounds 2.149 ms, projected bounds 1.923 ms, spatial bounds 1.818 ms, deformation scale 5.605 ms

Batch edits visit the selected indices once and copy the node array only when values change. Unedited node objects and element arrays remain shared with immutable history snapshots. Nearest-node selection builds a local adjacency set once; bounds use bounded-memory scans instead of spread arguments. Visual grid density is capped independently of physical mesh resolution.

The browser regression imports a 1,000-node model through PWDT, then exercises camera changes, window resize, selection, geometry replacement, undo, context loss/restoration, and switching back to 2D. Camera actions made no additional shader compilations, GPU buffer allocations, or geometry uploads. One program and nine buffers remain live while mounted; all are released on exit. GPU drawing is clipped to the SVG picking region and the SVG frame does not paint an opaque layer over the geometry. The test observed no WebGL errors. It does not use or stop installed services, and its temporary frontend/backend workspace is removed after the run.

Remaining limits: SVG picking still scales with visible geometry; whole-workbench state changes can still rebuild derived scene data, including on window resize. Dense plane fields, sustained high-density frame rates, and installed WKWebView behavior require separate qualification. No new WASM, Node runtime service, or long-lived global geometry cache was introduced by this optimization.

1.6.x

Stabilize the current viewport contract

Finish the separation between simulation truth and visual representation. This is the last stage where SVG remains the primary renderer for most result views.

Must land

  • result surface contract: define which result fields are viewable, selectable, exportable, and benchmarked per study family
  • render diagnostics: expose node count, element count, render-window limits, and progressive-render state in the workbench UI
  • field fallback policy: when density is too high, fall back to summary, hotspot, slice, or sampled views instead of freezing the viewport
  • selection integrity: keep picking, node focus, element focus, and workflow trace links stable even under partial render budgets

Must not attempt yet

  • full viewport rewrite
  • unbounded multi-layer overlay rendering
  • cinematic animation polish before field correctness
1.7.x

Introduce a dedicated plane-field renderer

This is the real turning point. The highest pressure area is not the whole workbench at once. It is 2D plane-field rendering for dense scalar and vector results.

Must land

  • new render lane: add a dedicated plane-result subrenderer on Canvas, WebGL, or WebGPU, without rewriting all workbench chrome
  • triangle and quad support: same field view path must support heat, electrostatic, structural plane, and thermo plane studies
  • palette contract: unify contour palette, clamps, outlier handling, legend generation, and no-data behavior
  • deformation composition: allow deform-only, field-only, and deform-plus-field modes without duplicating simulation transforms
  • render benchmarks: establish practical targets for small, medium, and stress-case plane meshes

Success condition

Advanced plane operators become believable because the viewport can display dense fields directly instead of reducing everything to sampled SVG shapes.

daji 3.x

Make multi-physics visualization composable

Once plane-field rendering is real, the next step is controlled layering. This is where electrostatic-to-heat-to-thermo chains start feeling like a native simulation language instead of several separate reports.

Must land

  • layer stack: explicit visibility and order for deformation, scalar field, vector glyphs, constraints, loads, selection, and warnings
  • workflow-linked views: clicking a workflow node can drive the active result layer without rebuilding the whole viewport state
  • cross-operator comparison: let users compare source field, bridged field, and downstream response inside one visual session
  • snapshot discipline: viewport state snapshots must stay bounded in memory and intelligible in audit exports
daji 3.x+

Converge toward a true FEM creation viewport

Only after the field renderer and layer system exist should the project lean into heavier viewport ambitions.

  • space-view maturity: improve 3D structural rendering, clipping, and density-aware picking
  • material and operator previews: shader-like previews for workflow templates, operator packs, and reusable composite assets
  • interactive analysis modes: probes, cuts, path plots, temporal comparisons, and guided diagnosis surfaces
scope

What can ship now without waiting

  • operators: new electrostatic, heat, thermal, and transform operators
  • bridge contracts: richer cross-operator field transfer rules and reduction policies
  • workflow features: graph insertion, composite templates, run traces, benchmark hooks, audit exports
  • SDK growth: headless workflow and operator execution contracts

These stay valid because the rendering layer is a consumer of simulation truth, not the truth itself.

guardrails

What would be a mistake right now

  • mistake 1: treating SVG batching as a permanent high-density rendering solution
  • mistake 2: coupling workflow semantics to whatever the current viewport can easily draw
  • mistake 3: shipping heavy visual layering before a memory and snapshot budget exists
  • mistake 4: benchmarking only solver time while ignoring result-surface cost
benchmarks

Render metrics that should become first-class

  • time to first view: time until a user sees a meaningful result surface
  • time to full detail: time until all intended layers are available
  • interactive floor: pointer and selection responsiveness while the viewport is busy
  • memory ceiling: viewport plus snapshot memory under repeated workflow runs
  • degrade quality: whether fallback modes stay honest instead of silently dropping important context
bottom line

Simple project stance

The current renderer is enough to support serious operator progress. It is not enough to be the final host for the most advanced simulation features. So the correct strategy is not to pause feature work. The correct strategy is to keep advancing operators while preparing a dedicated field-render lane in the next minor line.
